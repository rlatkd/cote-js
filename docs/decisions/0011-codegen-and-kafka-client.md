## 결정 1 — 코드젠 = buf CLI + **로컬 플러그인** (BSR 미사용)

`buf generate`로 `.proto` → 언어별 소스를 생성한다. 설정은 [`contracts/buf.yaml`](../../contracts/buf.yaml)·[`buf.gen.yaml`](../../contracts/buf.gen.yaml).

**사용자 방침 반영 — 외부 SaaS 의존 금지(오픈소스는 무방).** 최초 추천은 buf의 *원격 플러그인*이었으나, 그것이 Buf사 호스팅 서비스(BSR)에 의존한다는 점을 사용자가 지적해 재검토했다. buf는 두 층으로 분리된다:

| 구성요소 | 정체 | 채택 |
|---|---|---|
| buf CLI | 오픈소스(Apache 2.0), 로컬 바이너리 | **채택** |
| BSR (Buf Schema Registry) | Buf사 호스팅 SaaS | **미사용** |

플러그인(`protoc-gen-go`, 오픈소스)을 로컬 설치(`go install`)하고 `local:`로 참조하면 **전 구성이 오픈소스 + 로컬 실행**이 된다. 포기하는 것은 "플러그인 설치 생략"이라는 편의 하나뿐.

**protoc 직접 사용 대비 이점**(플러그인은 어차피 양쪽 다 로컬 설치이므로 순이득):
- 명령줄 인자(include 경로·출력 경로·옵션) 대신 **선언적 설정 파일** — 폴리글랏 모노레포에서 소비자(Go/JVM)마다 명령을 재현할 필요가 없다.
- `buf lint` — proto 스타일·구조 검사.
- **`buf breaking` — [0009]에서 Schema Registry를 보류하며 포기한 "호환성 강제"를 메꾼다.** git의 이전 커밋과 대조해 와이어 호환성을 깨는 변경(필드 번호 변경·타입 변경·필드 제거)을 검출한다.

**락인 없음**: 산출물은 표준 Protobuf 생성 코드이고 원본은 표준 `.proto`라, buf를 버리고 protoc로 돌아가도 계약·생성물이 그대로다.

**부속 결정 — 생성물은 커밋한다.** web의 `schema.d.ts`와 같은 관행([0007]). 빌드에 도구가 없어도 되고, **계약 변경이 PR diff에 드러난다.**

**미결(다음 슬라이스)**: JVM(api) 생성기. Kotlin/Java 생성은 protoc 내장 생성기를 요구하므로 도구 확보 방식(Gradle protobuf 플러그인 vs protoc 바이너리)을 api 배선 시 정한다. 현재 `buf.gen.yaml`에는 Go 플러그인만 있다.

## 결정 2 — Go Kafka 클라이언트 = franz-go

| 후보 | 판단 |
|---|---|
| **franz-go (채택)** | 순수 Go(cgo 없음) — Windows·macOS 개발 환경에서 빌드 마찰 0. 프로토콜 커버리지가 가장 넓고(0.8~4.x), 프로듀서·컨슈머·트랜잭션·관리 API가 한 클라이언트에 통합. 성능도 최상위 |
| confluent-kafka-go | cgo로 librdkafka를 감싸므로 Windows 개발에서 툴체인 마찰. "인프라만 도커, 앱은 네이티브"([0007] 개발 원칙)와 궁합이 나쁨 |
| sarama | 가장 널리 쓰였지만 API가 무겁고 리밸런스 관련 함정이 많다고 알려짐(유지보수도 약화) |
| segmentio/kafka-go | 순수 Go·단순하지만 프로토콜 커버리지가 franz-go보다 좁음 |

핵심 기준은 **cgo 여부**(개발 환경 마찰)와 **프로토콜 완전성**(추후 트랜잭션·관리 API 필요 시 클라이언트 교체를 피함)이었다. 성능은 결정 요인이 아니었다(우리 처리량에서 넷 다 충분).

오브젝트 스토리지 클라이언트는 **minio-go**(오픈소스, S3 호환) — 배포 시 실제 S3로 바꿔도 코드가 유지된다.

## 결정 3 — 전달 보장 = at-least-once (수동 오프셋 커밋)

**자동 커밋을 끄고, 채점을 마친 뒤에 커밋한다.**

- 자동 커밋이면 "커밋 → 채점 중 워커 사망" 순서에서 **제출이 통째로 유실**된다. 사용자 화면은 영원히 "채점 중"에 머문다.
- 수동 커밋이면 같은 상황에서 **재시작 후 다시 채점**한다(중복). 즉 **유실 대신 중복을 택했다** — 채점은 순수 함수에 가까워(같은 코드·같은 케이스 → 같은 판정) 중복의 해가 작고, 유실은 사용자에게 직접 보이는 실패이기 때문.
- 중복 결과의 처리는 **api 몫**: `submission_id`로 멱등하게 저장한다(결과 토픽 키도 `submission_id` — 같은 제출의 결과가 같은 파티션에 순서대로 간다). api 배선 시 구현.
- exactly-once(Kafka 트랜잭션)는 배제 — 채점의 부수효과가 외부(Docker 실행)에 있어 트랜잭션이 그것까지 되돌리지 못한다. 비용만 크고 보장은 불완전.

**부속 규칙 — poison message**: 역직렬화 실패 메시지는 재시도해도 같은 결과이므로 로그만 남기고 건너뛴다(무한 재시도로 레인을 막지 않는다). DLQ(dead letter queue)는 운영 단계에서 재검토.

## 결정 4 — QoS 레인 우선순위 구현 = 폴 배치 내 정렬

[0006]의 3레인(run·submit·batch)을 **토픽 분리**로 두고, 워커는 셋을 함께 구독한 뒤 **한 번의 폴에서 받은 레코드를 레인 우선순위로 정렬**해 처리한다(run < submit < batch, 안정 정렬이라 같은 레인 내 도착 순서는 보존).

- 대안(레인별 전용 워커 풀)은 워커 수를 3배로 만들고 레인별 유휴 자원이 생긴다. 단일 워커가 우선순위를 판단하는 편이 자원 효율이 좋다.
- 한계(문서화): 이 방식은 **한 폴 안에서의** 우선순위다. batch를 이미 집어 든 뒤 run이 도착하면 그 batch가 끝나야 run이 실행된다. 엄밀한 선점이 필요해지면 레인별 동시성 슬롯 분리로 확장한다(워커 수평 확장 = M2 범위).

- **왕복**: judgeprobe로 번들 업로드(MinIO) → 제출 발행 → judged 채점 → 결과 토픽 소비까지 관통. AC/WA 모두 케이스별 결과 포함해 정상 수신.
