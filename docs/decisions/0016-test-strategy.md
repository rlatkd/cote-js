# 0016. 테스트 전략 — 선별적 TDD와 "테스트하지 않을 것"의 명시

- **상태**: Accepted
- **일자**: 2026-07-28
- **관련**: [guides/verification.md](../guides/verification.md)(수동 검증 절차 — 이 ADR 이전의 유일한 안전망)

## 맥락 — 출발점은 테스트 0개

2026-07-28까지 이 프로젝트의 자동화 테스트는 **한 개도 없었다**. 검증은 전부 수동이었다(curl 스위트·`judgecli` 직접 실행·psql 조회). 그 절차를 [verification.md](../guides/verification.md)에 적어두고 매번 손으로 재현했다.

이 방식이 무의미하진 않았다 — 인코딩 버그·타임존 어긋남·컨테이너 고아 프로세스를 실제로 이걸로 잡았다. 그러나 **한 번 잡은 버그가 다시 들어와도 아무도 못 잡는다.** 서비스가 3개(web·api·judge)로 늘어난 시점에 회귀 위험이 실재하게 됐다.

**TDD는 한 번도 하지 않았다.** 순서는 늘 "구현 → 수동 검증 → 문서화"였다.

## 결정 1 — 전면 TDD가 아니라 **선별적 TDD**

| 대상 | 방식 | 근거 |
|---|---|---|
| 도메인 규칙·정책(판정·출력 비교·멱등·상태 전이·자원 보정) | **테스트 먼저** | 규칙이 명확하고 변경이 적다. 테스트가 곧 사양서 — 산문보다 정확하다 |
| 계약 경계(proto 왕복, DTO↔도메인) | 구현 후 고정 | 계약 위반은 조용히 퍼지므로 잡아야 하지만, 형태가 코드젠에 종속 |
| 인프라 어댑터(Kafka·Docker·S3) | 구현 후, **핵심 불변식만** | 탐색적이라 설계가 자주 바뀐다 |
| UI 컴포넌트 | 최소 | 변경이 잦고 검출력이 낮다 |
| 생성 코드(protobuf)·프레임워크 동작 | **테스트하지 않음** | 남의 코드를 테스트하는 것 |

**왜 전면 TDD가 아닌가**: 초반은 탐색적 설계였다. Kafka·MinIO·Docker 샌드박스를 처음 붙이는 단계에선 "무엇이 옳은 동작인지"를 몰라 테스트를 먼저 쓸 대상이 없었다. 실제로 오늘만 `Runner` 포트(2메서드→1), Kafka 클라이언트(reactor-kafka→직접), 시간 타입(LocalDateTime→Instant), 언어 처리(하드코딩→레지스트리)를 갈아엎었다 — **촘촘한 테스트가 붙어 있었다면 각 변경 비용이 몇 배**였을 것이다.

**왜 정책 로직은 TDD인가**: 출력 비교 규칙·판정 우선순위는 탐색이 아니라 **결정**이었다. `{"중간 공백은 의미가 있다", "12\n", "1 2\n", false}` 한 줄이 문단 하나보다 정확하다.

## 결정 2 — 커버리지를 목표로 삼지 않는다

**커버리지 숫자를 높이면 실제 검출력이 오히려 떨어질 수 있다.** 오늘 실제로 잡은 버그를 보면 이유가 분명하다:

| 실제 버그 | 단위 테스트로 잡히나 |
|---|---|
| reactor-kafka ↔ kafka-clients 4.x 바이너리 비호환 | ❌ 런타임에만 |
| judge UTC vs api 로컬 → 9시간 어긋남 | ❌ 경계를 실제로 넘어야 |
| `@Bean` 이름이 컴포넌트명과 충돌 | ❌ 스프링 컨텍스트 기동 필요 |
| JVM에 `RLIMIT_AS`를 걸면 기동조차 못 함 | ❌ 실제 컨테이너 필요 |
| Windows 인코딩(JSONB 한글 깨짐) | ❌ 실제 DB·JVM 설정 필요 |

**전부 경계·환경 문제**다. 커버리지를 목표로 하면 손이 가는 곳은 반대로 테스트하기 쉬운 순수 로직이라, **숫자는 오르는데 위험은 그대로**인 상태가 된다 — "검증됐다"는 착각이 가장 큰 리스크다.

## 결정 3 — 목(mock)의 중간 지대를 피한다

- 도메인·정책: **목 없이** 순수하게
- 인프라 어댑터: 목 대신 **진짜 인프라**(Testcontainers)
- **금지**: "목으로 인프라 흉내내기" — 그 목은 내가 상상한 Kafka이지 실제 Kafka가 아니다. 위 표의 1번이 정확히 그 경우로, 목이었다면 영원히 못 잡았다.

## 결정 4 — 금지 규칙 3가지

1. **측정값 assertion 금지** — 채점기는 시간을 재는 도메인이라 `24ms` 같은 값에 의존하면 머신 부하에 따라 랜덤 실패한다. **판정 종류만 검증하고 측정값은 검증하지 않는다.**
2. **구현을 복사하는 assertion 금지** — 매핑 함수 테스트에서 매핑을 다시 쓰는 식. 변경 시 양쪽을 함께 고쳐야 해 회귀 검출력이 0인데 유지비만 든다.
3. **flaky는 고치거나 삭제** — 방치 금지. 빨간불 하나가 "무시해도 됨" 문화를 만들고, 그 순간 테스트 전체가 무의미해진다.

## 결정 5 — 임의 정책값은 **불변식**으로만 테스트한다

시간 보정 배수(Python ×3, Java ×2)는 관행 기반의 임의값이지 측정 결과가 아니다([ADR-0013](0013-judge-language-expansion.md)). 이를 테스트에 구체값으로 박으면 "왜 3인가"를 다시 묻지 않게 된다 — **테스트는 "이게 옳다"가 아니라 "이게 현재 결정이다"만 말하는데 사람은 전자로 읽는다.**

그래서 `TimeFactor == 3.0`이 아니라 `TimeFactor >= 1`(제한을 줄이면 안 된다)이라는 불변식을 검사한다.

## 알려진 리스크 (이 결정을 채택하면서 감수하는 것)

- **환경 의존**: Testcontainers는 Docker에 의존하는데 이 개발 환경의 Docker Desktop이 불안정하다(2026-07-28 하루에 두 번 중단). 실패가 "코드 문제"인지 "환경 문제"인지 구분이 안 되면 신뢰가 떨어진다 → 통합 테스트는 **핵심 불변식만** 두고 개수를 늘리지 않는다.
- **테스트가 설계를 굳힌다**: 아직 problem·plagiarism 서비스가 통째로 남아 경계가 더 움직인다. 그래서 어댑터 테스트를 넓히지 않는 것이 의도된 선택이다.

### 대역(fake)에 대한 판단 — "목 금지"와 모순이 아닌 이유

`SubmissionServiceTest`는 포트의 손수 구현(fake)을 쓴다. 이는 [결정 3]의 금지 대상("목으로 인프라 흉내내기")과 다르다: **우리가 정의한 포트의 최소 구현**이지 Kafka·S3의 의미론(파티션·재시도·일관성)을 모사하지 않는다. 인프라 의미론이 걸린 검증(멱등 저장)은 진짜 Postgres로 한다.

### 첫 실행 후 검토에서 드러난 것 (2026-07-28)

CI가 **통과했다고 검증된 것은 아니었다.** 잡 3개가 초록불이었지만 실제로는:

| 발견 | 실상 | 조치 |
|---|---|---|
| `buf breaking`이 `pull_request`에만 걸려 있었다 | 이 저장소는 **main 직접 푸시**가 주 흐름(머지 커밋 0개)이라 **한 번도 실행된 적 없음**. Schema Registry 대신 세운 강제 장치가 무력 | push에서는 **직전 커밋 기준**으로 검사 추가 |
| 생성물 드리프트를 아무도 안 본다 | `.proto`만 고치고 재생성을 잊으면 원본과 생성 코드가 어긋난 채 전부 통과한다([ADR-0011]의 "생성 후 커밋" 규율이 사람 규율로만 존재) | CI에서 재생성 후 `git diff`로 강제 |
| 저장소 blob에 **CRLF**가 담겨 있었다 | 리눅스 러너는 CRLF로 체크아웃 → `buf generate`는 LF로 씀 → 위 드리프트 검사가 **매번 오탐**할 상태 | `.gitattributes`에 `* text=auto eol=lf` + 검사에 `--ignore-cr-at-eol` |

**교훈**: 초록불은 "검사가 통과했다"이지 "검사가 실행됐다"가 아니다. **조건부 스텝(`if:`)은 그 조건이 실제 워크플로에서 성립하는지 확인해야** 의미가 있다.

### CI에서 의도적으로 **제외한** 것

- **샌드박스 실채점**(러너 이미지 3종 빌드 + 컨테이너 실행): 이미지 빌드가 느리고 시간 측정이 머신 부하에 민감해 flaky 위험이 크다([결정 4] 금지 규칙 1·3). [verification.md](../guides/verification.md)의 수동 절차로 남긴다.
- **전 구간 E2E**(Kafka+MinIO+web): 같은 이유. 인프라 4종을 CI에서 띄우면 실패 원인이 코드인지 환경인지 흐려진다.

## 부수 발견 — 테스트가 드러낸 설계 문제

`aggregate()`가 파일시스템을 직접 읽는다(`out/NN.out`). 판정 로직만 테스트하려는데 임시 디렉토리가 필요했다. 출력 읽기를 주입 가능한 형태로 분리하면 순수 함수가 된다 — **테스트를 먼저 썼다면 이 설계가 안 나왔을 것**이고, TDD의 설계 피드백 효과를 보여주는 실제 사례다(TODO에 개선 항목으로 등록).
