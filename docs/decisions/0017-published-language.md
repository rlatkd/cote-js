- **상태**: Accepted
- **일자**: 2026-07-28
- **관련**: [0010](0010-contracts-root-group.md)(`contracts/` 신설), [0015](0015-cross-service-time-contract.md)(시간 규약 — 이 방향의 첫 사례)

## 맥락 — 사용자 발제에서 출발

타임존 작업을 보던 사용자 질문: *"MSA 환경인데 시간처럼 공통으로 쓰는 건 공통화된 인터페이스가 필요하지 않나? 각 서버별 컨버터만으로 충분한가?"* — 그리고 곧 범위를 명확히 했다: *"타임존을 말한 게 아니라 **그런 뉘앙스의 도메인**"*(= 공통 관심사 일반). 최종 방향: ***"contracts는 말 그대로 계약. 서비스 간의 확실하고 이상적인 시스템의 계약관계를 명시하고 싶다."***

## 개념 정리 — 질문에는 이미 이름이 있다

DDD 컨텍스트 매핑의 어휘로 갈린다:

| 개념 | 뜻 | 대응물 |
|---|---|---|
| **Anticorruption Layer** | 남의 모델을 내 모델로 **각자 번역** | "서버별 컨버터" |
| **Published Language** | 서로 다른 컨텍스트가 교환에 쓰는 **공통 스키마** | `contracts/`의 protobuf |
| Shared Kernel | 공통 모델을 여러 팀이 함께 소유 | 사내 공통 라이브러리 |

원 질문은 **"ACL만으로 충분한가"**였고, 답은 이렇다: **공표 언어가 있으면 컨버터가 얇아지고, 없으면 N×N 번역이 된다.** 서비스 3개는 감당되지만 5개(problem·plagiarism 예정)가 되면 "A는 시간을 이렇게, B는 저렇게" 해석이 갈라진다.

## 결정 1 — `contracts/`의 정체를 재정의한다

**"채점 메시지 정의소" → "서비스 간 공표 언어"**. 도메인별 메시지(`judge/v1`) 옆에 **모든 서비스가 공유하는 개념**을 두는 `common/v1`을 신설한다.

```
contracts/proto/
├─ common/v1/     모든 서비스가 공유하는 개념
│  ├─ trace.proto   상관관계(추적) 컨텍스트
│  └─ error.proto   실패의 공통 표현
└─ judge/v1/      도메인별 메시지 (common을 import)
```

**핵심 이점: 규약이 문서가 아니라 타입이 된다.** "시간은 UTC로 쓰자"를 문서에 적으면 지키는지 알 수 없지만, 계약이 `google.protobuf.Timestamp`를 쓰면 어느 언어로 코드를 생성하든 **그 타입을 쓸 수밖에 없다.** 강제 지점이 사람의 규율에서 코드젠으로 옮겨간다.

## 결정 2 — 첫 공통 타입: 추적(trace)과 실패(error)

### TraceContext — 흐름을 잇는 실

제출 하나가 `web → api → Kafka → judge → Kafka → api`를 지나는데, 지금까지는 각 서비스 로그를 `submission_id`로 **눈으로 이어붙여야** 했다. 서비스가 늘면 불가능해지고, 각자 다른 필드명을 쓰기 시작하면 영영 못 잇는다.

- 형식은 **W3C Trace Context 표준**(trace_id 32자 hex, span_id 16자 hex)을 따른다 — 나중에 OpenTelemetry를 얹을 때 우리 포맷을 번역할 필요가 없다.
- 흐름의 시작점(api가 제출을 접수하는 순간)에서 한 번 만들고, **judge는 이어받아 그대로 결과에 실어 보낸다**(새로 만들면 실이 끊긴다).

### Error — "무엇이 실패했나"가 아니라 "받는 쪽이 무엇을 해야 하나"

judge는 실패를 문자열 하나(`error_message`)로 보냈다. 받는 쪽은 그 문자열을 보고 **재시도할지·사용자에게 보여줄지·운영자를 부를지를 스스로 추측**해야 했고, 추측이 서비스마다 달라지면 같은 실패가 다르게 처리된다.

그래서 판단에 필요한 정보를 **발신자가 명시**하게 한다:

| 필드 | 역할 |
|---|---|
| `code` | 기계가 분기하는 안정 식별자(문구가 바뀌어도 불변) |
| `origin` | **누구 귀책인가** — `CALLER`(유저 코드) / `PROVIDER`(채점 시스템) |
| `retryable` | **재시도해도 되는가** — 발신자만 아는 정보다 |
| `message`·`detail` | 사람이 읽는 설명·진단 부속 |

적용 예: 컴파일 실패는 `CALLER` + `retryable=false`(같은 코드는 같은 결과), 채점기 내부 오류는 `PROVIDER` + `retryable=true`(재채점이 의미 있음). **정상 판정(오답·시간초과)은 실패가 아니다** — 채점은 성공했고 결과가 오답일 뿐이라 `failure`가 비어 있다.

## 결정 3 — 필드 교체는 "둘 다 채우는 기간"을 거친다

`error_message`를 바로 지우지 않고 `deprecated`로 표시한 뒤 **`failure`와 함께 채운다.** 소비자 전환이 끝나면 제거한다.

- 이유: 발행자와 소비자가 **다른 서비스**라 동시에 배포되지 않는다. 필드를 즉시 제거하면 아직 옛 필드를 읽는 소비자가 깨진다.
- 이것이 스키마 진화의 기본 규율(추가 → 병행 → 제거)이며, `buf breaking`이 그 규율의 자동 검사 역할을 한다.

## 검토했으나 지금은 아닌 것

| 대안 | 판단 |
|---|---|
| 언어별 공통 라이브러리(Go·Kotlin·TS·Python 4벌) | **스택이 단일하면 최적해**지만(사내 스타터 형태) 4개 언어면 4벌을 유지해야 하고 버전이 어긋나면 규약이 갈라진다. 폴리글랏에선 무게중심이 라이브러리 → 코드젠·플랫폼으로 이동 |
| 서비스 메시(Istio) | 통신 동작(재시도·mTLS·트레이스 전파)을 앱 밖에서 강제하는 정석이지만 **페이로드의 의미는 못 잡는다**. 게다가 K8s 이전·서비스 3개 규모엔 과설계 → M5 재검토 |
| 골든 패스 템플릿(Backstage)·정책 코드화(OPA) | 서비스가 수십 개일 때의 도구 |

**강제 지점은 관심사 종류에 따라 갈린다**는 것이 이 논의의 결론이다: **값·메시지의 의미 → IDL+코드젠**(이 ADR), **통신 동작 → 사이드카/메시**, **서비스 내부 규율 → lint·CI 게이트**(미도입).

## 검증 (2026-07-28 실측)

- `buf lint` 통과, Go·JVM 양쪽에 `common/v1` 생성 확인.
- **추적 전파 확인**: 제출 47에 대해 api 로그(`채점 요청 발행 … trace=ae511fd4…`)와 judge 로그(`채점 완료 … trace_id=ae511fd41f81908e1b3d632eb52006d6`)에 **같은 trace_id**가 찍혔다 — 서비스 경계를 건너 흐름이 이어진다.
