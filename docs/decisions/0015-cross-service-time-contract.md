# 0015. 서비스 경계의 시간 규약 — UTC 절대시각으로 통일

- **상태**: Accepted
- **일자**: 2026-07-28
- **관련**: [0012](0012-api-judge-wiring.md)(9시간 어긋남을 겪은 곳), [0010](0010-contracts-root-group.md)(공표 언어)

## 맥락 — 무엇이 깨졌나

[0012] 구현 중 같은 행에서 `submittedAt 23:00`, `judgedAt 14:00`으로 **9시간 어긋나는** 데이터가 나왔다. 원인을 층별로 보면:

| 층 | 쓰던 것 | 성격 |
|---|---|---|
| judge → api (proto) | `google.protobuf.Timestamp` | **절대시각**(UTC epoch) — 모호함 없음 |
| api 도메인 | `LocalDateTime` | **존 없는 벽시계 값** — "몇 시"만 있고 "어디의 몇 시"가 없음 |
| DB | `TIMESTAMP`(without time zone) | 마찬가지로 존 없음 |

**계약(proto)은 처음부터 옳았다.** 깨진 건 api가 그것을 **존 없는 타입에 담는 순간**이었다. 당시엔 소비 지점에서 로컬존으로 변환해 증상만 덮었다.

## 결정 — 저장·전달은 절대시각, 지역 시간 변환은 표시에서만

```
경계(IDL)     google.protobuf.Timestamp   UTC epoch — 다른 해석의 여지가 없음
저장(DB)      timestamptz                 Postgres가 내부적으로 UTC 정규화
도메인(코드)   Instant / time.Time         존 없는 타입(LocalDateTime) 사용 금지
표시(web)     그때만 지역 변환             브라우저가 사용자 시간대를 안다
```

**핵심 원리: 컨버터를 잘 만드는 문제가 아니라, 모호함을 표현할 수 없는 타입만 쓰는 문제다.** `LocalDateTime`은 자신이 서울인지 UTC인지 모르기 때문에, 어떤 변환 코드를 붙여도 그 모호함은 사라지지 않는다. 네 층이 전부 절대시각 타입이면 중간에 변환이 몇 개 있든 틀릴 수가 없다.

### 검토한 대안

| 대안 | 판단 |
|---|---|
| 서비스마다 컨버터를 두고 규약은 문서로 | **배제** — 실제로 그렇게 하다 깨졌다. 문서는 강제력이 없고, 존 없는 타입이 남아 있는 한 재발한다 |
| 언어별 공통 시간 라이브러리(Go·Kotlin·TS·Python 4벌) | **배제** — 시간은 **표준 표현이 이미 존재**하는 값이라 표준 자체가 인터페이스다. 4벌을 만들어 유지하는 비용이 얻는 것보다 크다 |
| **표준 타입 + 3중 강제 (채택)** | IDL·DB 컬럼 타입·도메인 타입이 각각 불변식을 들고 있어, 한 층만 지켜도 나머지가 어긋나면 드러난다 |

### DTO 표현도 바꿨다

응답을 `"2026-07-28 21:30:04"`(형식 있는 로컬 문자열)에서 **ISO-8601 절대시각**(`"2026-07-28T12:30:04.992Z"`)으로 바꿨다. 표시 형식은 화면의 관심사이므로 web이 지역 시간으로 변환한다 — 제한값 수치화([0012])와 같은 원칙("데이터인가 표현인가").

## 더 큰 문제 — 클럭 스큐 (지금은 미해결, 방침만 고정)

타임존을 통일해도 **서로 다른 서버의 시계가 정확히 같지는 않다.** `submitted_at`은 api의 시계가, `judged_at`은 judge의 시계가 찍는다. 심하면 채점 완료가 제출보다 이른 데이터가 나온다.

**방침: 순서 판단에 벽시계를 쓰지 않는다.** 순서가 필요하면 논리적 근거(Kafka 오프셋·시퀀스·상태 전이)를 쓰고, 벽시계는 표시와 대략적 소요시간 측정에만 쓴다. 현재 코드는 순서 판단에 시각을 쓰지 않아 문제가 없지만, 채점 SLA 모니터링(제출↔결과 조인) 같은 기능이 생기면 바로 부딪힌다.

## 파급 — 이 규약이 첫 사례인 이유

이 결정은 "시간"에 국한되지 않는다. 폴리글랏에서 **경계 규약으로 못 박아야 하는 값**들의 첫 사례다:

| 값 | 상태 |
|---|---|
| 시간 | **이 ADR로 확정** |
| 문자 인코딩(UTF-8) | 한 번 데임(Windows JSONB 한글 깨짐) — 규약으로 명시 필요 |
| 식별자 | DB 시퀀스로 충분. 서비스가 발급하게 되면 UUIDv7/ULID 재검토 |
| 상관관계 ID(trace) | **없음** — 서비스 횡단 추적 불가 |
| 실패 표현 | 서비스마다 제각각 |

이들을 개별 문서 규약이 아니라 **공표 언어(proto 공통 타입)로 강제**하는 것이 다음 단계다(별도 ADR 예정).

## 검증 (2026-07-28 실측)

- V4 마이그레이션 후 기존 데이터 환산 확인: `14:22:10`(KST 기록) → `2026-07-09T05:22:10Z`.
- 새 제출 왕복: `submittedAt 12:30:04.992Z` → `judgedAt 12:30:05.850Z` (0.86초 차, 이전의 9시간 어긋남 소멸).
- 소비 지점의 존 변환 코드가 **사라졌다** — proto Timestamp → `Instant`는 변환이 아니라 그대로 옮기는 것이 됐다.
