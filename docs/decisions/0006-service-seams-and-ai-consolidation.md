# 0006. 서비스 이음새 규칙 + AI 서비스 병합 (3→2)

- **상태**: Accepted
- **일자**: 2026-07-25
> **명칭 노트(2026-07-25)**: 이후 [ADR-0008](0008-service-naming-and-group.md)로 서비스명이 개편됨 — arena→web, hub→api, setter→problem, scout→plagiarism, tester→problem의 validation 단계, judge 유지. 본문은 당시 명칭 그대로다(원문 동결 원칙).

## 맥락

서비스 목록과 네이밍은 [ADR-0003](0003-monorepo-structure.md)으로 확정됐지만, 전체 구성 리뷰 결과 **서비스 "사이"의 규칙이 미정의**였다:

1. 채점 결과가 유저에게 실시간으로 돌아오는 경로가 없음 (`… → DB 저장 → arena 표시`의 마지막 화살표가 미정)
2. DB 스키마 소유권 규칙이 없어 폴리글랏 서비스(hub·judge·scout·setter)가 같은 테이블을 공유할 위험
3. 코드 실행 요청이 사실 세 등급(예제 실행 / 정식 제출 / AI 검증 배치)인데 한 큐로 뭉개져 있어 배치가 유저 제출을 굶길 수 있음
4. 오프라인 문제 생성 파이프라인(생성→유사도→검증→검수→공개)의 **지휘자**가 없음
5. 파이프라인의 핵심 관문인 "사람 검수 게이트"의 UI가 계획에 없음
6. Redis 역할이 "캐시"라고만 적혀 있어 실제 용도가 불명확

또한 AI 3분할(setter/scout/tester)이 솔로 프로젝트 규모에서 과분해(오버엔지니어링)인지 재검토했다.

## 결정

### 1. AI 서비스 3→2 병합 — tester는 setter의 내부 모듈로

- **`setter`** = 출제 서비스 하나로 통합: **생성(LLM) + 품질 검증(정답 교차검증·TC 변별력) + 파이프라인 오케스트레이션**을 내부 모듈(`generate` / `validate`)로 가진다.
- **`scout`** = 독립 유지: 임베딩 모델을 메모리에 상주시키는 서빙 워크로드라 자원 특성(RAM/GPU·기동시간·스케일)이 확연히 다름 — 유일하게 분리 근거가 있는 경계.
- 근거: 생성과 검증은 항상 붙어 도는 **한 파이프라인의 앞뒤 단계**고, 둘 다 경량 I/O 오케스트레이션이라 네트워크 경계로 가를 실익이 없다. 분리는 "다르게 스케일해야 하는 곳"에만 긋는다. 도메인적으로도 실제 CP에서 problem setter가 출제+테스트 준비·검증을 함께 담당하므로 `setter` 명칭이 병합체를 정확히 표현한다.
- `tester`는 **폴더/서비스로 만들지 않고**, setter 내부 검증 모듈(파이프라인 단계 이름)로 강등한다. 검증 부하가 실제로 급증하면 그때 재분리(내부 모듈 경계를 유지해 분리 비용 최소화).

### 2. 채점 결과 실시간 경로 — judge는 DB에 쓰지 않는다

```
arena 제출 → hub → Kafka(제출 토픽) → judge
judge 판정 → Kafka(결과 토픽) → hub 소비 → DB 저장 + SSE로 arena 푸시
```

- judge는 **이벤트만 발행**하고 DB에 직접 접근하지 않는다(Go↔hub 간 스키마 공유 금지).
- arena 실시간 반영은 **SSE**(hub→arena 단방향 푸시)로 한다. WebSocket은 양방향이 필요해질 때 업그레이드.

### 3. DB 단일 작성자 원칙 — 스키마당 주인 하나

| 스키마(영역) | 주인(유일 작성자) | 비고 |
|---|---|---|
| 코어(회원·문제·제출·랭킹) | **hub** | 다른 서비스는 hub API/이벤트 경유 |
| 임베딩(pgvector) | **scout** | 문제 텍스트는 이벤트/API로 수신 |
| 출제 파이프라인(초안·검증 결과·검수 상태) | **setter** | 검수 승인 시 hub API로 공개 이관 |
| — | **judge = DB 접근 금지** | 결과는 Kafka 이벤트로만 |

### 4. 실행 요청 QoS 3레인

| 레인 | 요청 | 특성 | 정책 |
|---|---|---|---|
| `run` | 예제 실행 | 유저가 인터랙티브 대기 | 저지연 우선 |
| `submit` | 정식 제출 | 큐 대기 허용 | 표준 |
| `batch` | setter의 교차검증 대량 실행 | 급하지 않음 | 최저 우선순위 |

- Kafka 토픽(또는 우선순위)을 분리해 **배치 검증이 유저 트래픽을 절대 굶기지 않게** 한다. judge 워커는 레인별 소비 정책을 가진다.
- setter의 검증도 **judge를 재사용**한다(샌드박스를 두 번 만들지 않는다) — 단 batch 레인으로만.

### 5. 오프라인 파이프라인 지휘자 = setter

`생성 → scout 질의(유사도) → 교차검증 → 사람 검수 대기` 상태머신을 **setter가 소유**한다. Airflow 등 워크플로 엔진은 규모에 맞지 않아 도입하지 않는다.

### 6. 사람 검수 게이트 UI — 새 서비스 아님

- **arena에 admin 라우트**(검수 큐: 생성 문제 열람·승인·반려) + **hub에 admin API**(승인 시 공개 전환).
- M3(AI 생성 파이프라인) 범위에 포함시킨다.

### 7. Redis 역할 명시 — "캐시" 금지, 용도 3개

1. **제출 rate limiting** (judge 보호 — 없으면 제출 폭탄에 채점 인프라가 죽는다)
2. **랭킹 리더보드** (sorted set)
3. **SSE 팬아웃 pub/sub** (hub 다중 인스턴스 대비)

## 검토한 대안 (배제)

- **API Gateway 서비스**: hub가 이미 단일 진입점. K8s 이관 시 인그레스가 커버 → 불필요.
- **Airflow/워크플로 엔진**: 규모 불일치(파이프라인 1개) → setter 내 상태머신으로 충분.
- **judge의 직접 DB 쓰기**: Go와 Prisma가 같은 스키마를 이중 소유하게 됨(마이그레이션 충돌) → 금지.
- **WebSocket**: 채점 알림은 단방향이라 SSE로 충분. 필요해지면 그때 업그레이드.
- **AI 3분할 유지**: 서비스 경계가 "설명하기 좋은 곳"이 아니라 "다르게 스케일하는 곳"에 있어야 함. setter/tester 분리는 전시용 분해(오버엔지니어링)로 판정.
