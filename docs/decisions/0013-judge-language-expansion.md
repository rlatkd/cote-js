# 0013. judge 언어 확장 — 지원 범위·공용 하니스·언어별 자원 정책

- **상태**: Accepted
- **일자**: 2026-07-28
- **관련**: [0009](0009-judge-kickoff-async-and-contracts.md)(첫 슬라이스 Python 단독), [architecture/judge.md](../architecture/judge.md)

## 맥락

[0009]에서 "첫 슬라이스는 Python 단독"으로 정하고 executor에 컴파일 단계 **자리만** 만들어 뒀다. 그 결과 세 가지 문제가 남아 있었다:

1. **UI와 채점기의 불일치** — web 에디터와 api enum은 4개 언어(Python·C++·Java·JavaScript)를 제공하는데 judge는 Python만 실행할 수 있었다.
2. **오판정** — 도커 어댑터가 언어를 보지 않고 무조건 Python 이미지를 띄우고 소스를 `main.py`로 썼다. C++로 제출하면 파이썬이 그 코드를 읽어 `SyntaxError` → **`런타임 에러`로 판정**된다. "미지원"이 아니라 **틀린 답을 주는 것**이라 더 나쁘다.
3. **컴파일 단계 미검증** — 인터페이스에 자리만 있고 한 번도 실행된 적이 없어 설계가 맞는지 알 수 없었다.

## 결정 1 — 지원 범위 = Python · Java · JavaScript (C++ 제거)

사용자 결정(2026-07-28): **프로토타입이므로 3종.** C++는 UI·api enum·시드 starterCode에서 **제거**한다 — 채점기가 지원하지 않는 언어를 UI가 약속하면 위 2번(오판정)이 재발한다.

- **Java가 남아 컴파일 경로는 그대로 검증된다.** 언어 범위를 줄여도 설계 검증에 구멍이 없는 이유.
- 언어를 더 늘릴지 논의에서 나온 판단: **"몇 개"보다 "어떤 범주"** — 인터프리터/네이티브 컴파일/VM 컴파일 각 범주가 채점기에 요구하는 게 다르다(컴파일 유무, 기동 비용, 메모리 강제 방식). 같은 범주 안에서 언어를 늘리는 것은 러너 추가의 반복일 뿐 설계 검증 가치가 낮다.
- 배제한 것: C++·C·Go·Kotlin·Rust — **프로토타입 범위 밖**. 러너 Dockerfile + 레지스트리 항목 추가로 언제든 붙는다.

### 언어 확장의 실제 비용(문서화)

언어를 늘리면 **곱해지는 것**이 셋 있다: ① 문제별 스타터 코드(문제 × 언어) ② 언어별 자원 한도 정책 ③ 러너 이미지 유지. 특히 ①은 지금 `starter_code` JSONB에 문제마다 전 언어 코드를 박아두는 구조라, 언어가 많아지면 **언어별 기본 템플릿 분리**가 선결 과제가 된다(TODO).

## 결정 2 — 언어 지식의 단일 진실원 = `internal/language` 레지스트리

이미지·소스 파일명·컴파일/실행 명령·메모리 강제 방식·자원 보정을 한 곳(`Spec`)에 모으고, executor는 소스 파일명을, 샌드박스 어댑터는 이미지·명령을 여기서 가져간다.

- 이전엔 이미지 상수(`pythonImage`)와 파일명(`main.py`)이 **서로 다른 파일에 하드코딩**돼 있었다. 언어 추가가 여러 파일 수정으로 번지는 구조.
- `Lookup()`은 미지원 언어에 **에러를 반환**한다 — 오판정 대신 명시적 실패(`INTERNAL_ERROR` + "지원하지 않는 언어: cpp (지원: [python java javascript])").

## 결정 3 — 하니스는 Go 단일 정적 바이너리 (언어별 하니스 폐기)

컨테이너 안에서 케이스를 순회하며 시간·메모리를 재는 하니스를 **Go로 다시 쓰고**, 각 러너 이미지에 멀티스테이지 빌드로 넣는다.

| 대안 | 배제 이유 |
|---|---|
| 언어별 하니스(파이썬용·자바용…) | 같은 로직이 언어 수만큼 복제된다. 측정·타임아웃·프로세스 킬은 언어와 무관한 로직 |
| 파이썬 하니스로 통일 | **Java·Node 이미지에까지 파이썬을 설치**해야 한다(이미지 비대·버전 관리 대상 증가) |
| **Go 정적 바이너리 (채택)** | `CGO_ENABLED=0` 정적 링크라 어느 베이스 이미지에도 그대로 얹힌다. judge가 Go라 코드도 한 저장소 안 |

**부수 효과(문서화)**: 하니스는 리눅스 API(프로세스 그룹 킬·`getrusage`)를 쓰므로 개발 머신(Windows) 빌드가 깨진다 → `//go:build linux` + 비리눅스 스텁으로 분리. 스텁은 실행되면 즉시 실패해 "개발 머신에서 잘못 돌리는" 사고를 막는다.

## 결정 4 — 메모리 한도 강제는 언어마다 다르다

**같은 방식으로 통일할 수 없다**는 것이 핵심 발견이다.

| 방식 | 적용 | 이유 |
|---|---|---|
| `RLIMIT_AS`(주소공간 상한) | Python | 인터프리터가 할당 실패로 `MemoryError`를 내며 스스로 죽는다 — 정확하고 즉각적 |
| 런타임 힙 옵션(`-Xmx`, `--max-old-space-size`) | Java · JavaScript | **JVM·V8은 힙과 무관하게 가상주소를 크게 예약**한다. `RLIMIT_AS`를 걸면 정상 코드도 **기동조차 못 한다** |

MLE 식별도 언어별 시그니처(`MemoryError` / `OutOfMemoryError` / `heap out of memory`)로 한다. 언어 중립적이지 않다는 한계는 남으며, 근본 해결은 cgroup 이벤트 기반(샌드박스 2단계).

## 결정 5 — 시간·메모리 보정 배수

문제의 제한값은 통상 C/C++ 기준이라 느린 런타임에는 보정을 준다(온라인 저지의 일반 관행). 보정이 없으면 **정상 풀이도 TLE**가 난다.

| 언어 | 시간 배수 | 메모리 여유 | 근거 |
|---|---|---|---|
| Python | ×3 | +32MB | 인터프리터 실행 비용 |
| Java | ×2 | +96MB | JVM 기동 + 힙 외(메타스페이스·스택·GC 구조체) |
| JavaScript | ×2 | +64MB | V8 기동·힙 오버헤드 |

**이 값들은 관행 기반의 임의값이며 측정 결과가 아니다.** 그래서 테스트는 구체값(3.0)을 박지 않고 **불변식**(`TimeFactor >= 1`)만 검사한다 — 값이 정답으로 굳는 것을 막기 위해([ADR-0016](0016-test-strategy.md)).

## 결정 6 — "컴파일 단계"를 실행 전 검증 단계로 일반화

컴파일이 없는 언어에도 **문법 검사**를 컴파일 단계로 넣는다: Python은 `py_compile`, JavaScript는 `node --check`.

- 이유: 문법 오류를 케이스마다 런타임 에러로 **반복 보고**하는 대신 `COMPILE_ERROR`로 **한 번에** 알린다. 사용자에게도 정확한 정보고(문법 오류지 로직 오류가 아님), 케이스 실행을 낭비하지 않는다.
- 결과: 세 언어 모두 실제 컴파일러·파서 메시지를 담아 `COMPILE_ERROR`를 낸다.

## 결정 7 — Runner 포트를 한 메서드로 통합

`Compile()` + `RunCases()` 2메서드 → `Run()` 1메서드([0009] 당시 설계의 개정).

- 나누면 **컨테이너를 두 번 띄워야** 하고(기동 비용 2배), 컴파일 산출물 전달을 바인드 마운트 잔존에 의존하게 된다.
- 한 번의 컨테이너 실행 안에서 "검증 → 케이스 실행"이 끝나는 게 자연스럽다. 하니스가 `compile.json` · `result.json`을 각각 쓰고 어댑터가 읽는다.

## 검증 (2026-07-28 실측)

| 언어 | AC | CE | TLE | MLE | RE |
|---|---|---|---|---|---|
| Python | ✅ 27ms | ✅ `File "main.py", line 1` | ✅ | ✅ | ✅ |
| Java | ✅ 110ms | ✅ `Main.java:3: error: ';' expected` | ✅ | ✅ | — |
| JavaScript | ✅ 46ms | ✅ `/judge/main.js:2` | — | ✅ | ✅ |

- **`COMPILE_ERROR` 판정 경로는 이번이 첫 검증**(설계 후 한 번도 실행된 적 없던 경로).
- 미지원 언어(`cpp`) → 오판정 대신 명시적 실패 확인.
