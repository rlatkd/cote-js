# 0014. 실행 모드 분리(run/submit)와 케이스별 채점 피드백

- **상태**: Accepted
- **일자**: 2026-07-28
- **관련**: [0006](0006-service-seams-and-ai-consolidation.md)(QoS 3레인), [0012](0012-api-judge-wiring.md)(api 배선)

## 맥락

web에는 "예제 실행"과 "제출" 두 버튼이 있는데, **예제 실행은 목업**이었다(가짜 결과를 지연 노출). 그리고 [0006]에서 QoS 3레인(run/submit/batch)을 설계해놓고 실제로는 `submit` 하나만 쓰고 있었다 — 레인 분리가 말로만 존재했다.

또 judge는 케이스별 판정을 결과 메시지에 담아 보내는데 **api가 종합만 저장하고 나머지를 버리고** 있었다.

## 결정 1 — 실행 모드를 도메인 개념으로 승격

`ExecutionMode { RUN, SUBMIT }`를 도메인에 두고, 제출 요청이 이를 받는다(생략 시 `SUBMIT`).

**모드가 가르는 것 셋:**

| | run (예제 실행) | submit (정식 제출) |
|---|---|---|
| 채점 데이터 | **공개 예제**(`example`) | **히든 케이스**(`test_case`) |
| QoS 레인 | `submission.run` | `submission.submit` |
| 채점 현황 노출 | 안 함 | 함 |

**공개 예제로 채점하는 이유**: run에 히든 케이스를 쓰면 사용자가 **예제 실행만으로 히든 데이터를 역추적**할 수 있다(출력을 조금씩 바꿔가며 통과 여부를 관찰). 채점 데이터의 기밀성은 문제의 변별력이므로, 모드에 따라 번들 자체를 다르게 만든다.

## 결정 2 — run 실행도 `submission` 테이블에 기록한다 (모드 컬럼으로 구분)

대안이었던 "기록하지 않고 메모리에서만 처리"를 배제했다:

- 결과는 Kafka 결과 토픽으로 **비동기로 돌아온다.** 상관관계 키가 `submission_id`이므로, 기록하지 않으려면 별도의 임시 id 공간과 인메모리 매핑을 따로 만들어야 한다 — **한 파이프라인을 두 가지 방식으로** 운영하게 된다.
- 기록하면 실행 이력이 남아 디버깅에도 쓸 수 있다.
- 대신 **조회에서 배제**한다: 채점 현황 목록은 `mode = 'submit'`만 조회(인덱스 포함). "기록은 하되 보이지 않는다".
- **한계(명시)**: SSE 스트림은 run 이벤트도 그대로 내보낸다(문제 화면이 자기 실행 결과를 받아야 하므로). 채점 현황 화면이 이를 걸러야 하며, 지금은 DTO의 `mode` 필드로 web이 판단한다.

## 결정 3 — 예제 번들도 claim-check 규약을 그대로 쓴다

`problem.example_bundle_key/sha256`을 두고 `test_bundle_*`와 **같은 방식**으로 발행·캐시한다. 공개 예제도 채점기 입장에선 그냥 케이스이므로 별도 경로를 만들지 않는다 — 번들 규약이 하나면 judge는 모드를 알 필요조차 없다(judge는 지금도 run/submit을 구분하지 않는다. 토픽이 다를 뿐).

## 결정 4 — 케이스별 결과를 저장한다

`submission_case` 테이블 신설. 근거는 **제품 성격**이다: 학습 플랫폼에서 "몇 번 케이스에서 왜 틀렸나"가 사용자 가치의 핵심이다([0009]에서 "첫 실패 후에도 끝까지 실행"을 택한 것과 같은 이유). judge가 이미 보내주는 데이터를 버리고 있었던 것.

- **멱등 구현**: 결과 반영 시 해당 제출의 케이스를 **전부 삭제하고 다시 삽입**한다. at-least-once에서 같은 결과가 두 번 와도 행이 늘지 않는 가장 단순한 방법(UPSERT보다 의도가 분명하다).
- **목록 조회에도 함께 싣는다**: 처음엔 SSE로만 케이스가 전달되고 목록 응답에는 항상 빈 배열이 나갔다 — **응답에 필드가 있는데 늘 비어 있으면 계약이 거짓**이 된다. 제출 목록 조회 시 케이스를 일괄 적재(N+1 회피)해 채운다.

## 검증 (2026-07-28 실측)

- **run 모드**: 히든 케이스가 **없는** 문제(2231)에 예제 실행 → 공개 예제로 채점되어 `맞았습니다`. judge 로그에서 `lane=submission.run` 확인(레인 분리가 실제로 동작).
- **채점 현황 제외**: 목록 응답의 모드 집합이 `['submit']`뿐, run 제출(id 34) 미포함.
- **케이스별 결과**: 3번 케이스(`9 9` → `18`)만 틀리게 만든 Java 풀이 제출 → 1·2·4·5번 `맞았습니다`, **3번만 `틀렸습니다`**, 종합 `틀렸습니다`.
