## 시스템 설계

### SSE vs WebSocket — 채점 알림엔 왜 SSE인가
채점 결과 알림은 **서버→클라이언트 단방향**이다. WebSocket은 양방향 채널이라 연결 관리(핸드셰이크 업그레이드·재연결·프록시 설정)가 더 무겁다. SSE(Server-Sent Events)는 일반 HTTP 위에서 동작하고 자동 재연결이 내장돼 있어 단방향 푸시엔 더 단순한 정답. 양방향(예: 실시간 협업)이 필요해지면 그때 업그레이드한다. **면접 포인트**: "기술 선택은 요구 방향성(단방향/양방향)부터 따진다." — 2026-07-25 12:48

### DB 단일 작성자 원칙 (single writer per schema)
폴리글랏에서 두 언어(예: Go와 Kotlin)가 같은 테이블에 쓰면 스키마 마이그레이션의 주인이 없어진다 — 한쪽이 컬럼을 바꾸면 다른 쪽이 런타임에 깨짐. 그래서 **스키마당 작성자 하나**를 규칙으로 박고, 다른 서비스는 API/이벤트로만 접근한다(judge는 아예 DB 접근 금지, 결과는 Kafka 이벤트). 이는 MSA의 "database per service" 패턴의 완화형이다. — 2026-07-25 12:48

### QoS 레인 분리 — head-of-line blocking
같은 큐에 성격이 다른 작업(인터랙티브 예제 실행 / 정식 제출 / AI 검증 배치)을 섞으면, 대량 배치가 앞을 막아 유저 요청이 굶는다(head-of-line blocking). 해법은 **레인(토픽/우선순위) 분리** + 소비자(judge 워커)의 레인별 소비 정책. 실무의 "배치와 온라인 트래픽을 절대 같은 풀에 두지 말라"와 같은 원리. — 2026-07-25 12:48

### 서비스 경계는 "다르게 스케일하는 곳"에 긋는다
AI를 3서비스로 쪼갰다가 2로 병합한 근거. 생성(LLM 호출)과 검증(교차검증 오케스트레이션)은 둘 다 경량 I/O 작업이고 항상 한 흐름으로 돌아서 네트워크 경계의 실익이 없다. 반면 임베딩 서빙(scout)은 모델을 메모리에 상주시키는 다른 종의 워크로드다(RAM/GPU·기동시간·스케일 단위가 다름). **경계 기준 = 배포·스케일 특성의 차이**이지, "설명하기 좋은 분해"가 아니다. — 2026-07-25 12:48

### 샌드박스 격리 3요소 (judge 예정)
남의 코드 실행의 격리는 커널 기능 3종의 조합: **cgroups**(CPU·메모리·프로세스 수 상한 — fork bomb 방어), **namespaces**(pid/net/mount 시야 격리 — 네트워크 차단), **seccomp**(허용 시스템콜 화이트리스트). Docker는 이 셋의 포장지일 뿐 컨테이너 하나로는 보안 경계가 아니다. Go를 judge에 쓰는 이유 중 하나가 이 커널 기능들의 레퍼런스 구현(runc/gVisor)이 전부 Go라는 것. — 2026-07-25 12:48

### claim-check 패턴 — 메시지 브로커에 대형 페이로드를 싣지 않는다
Kafka 메시지 상한(기본 ~1MB)에 대형 테스트케이스가 걸리는 문제의 표준 해법: **페이로드는 오브젝트 스토리지에, 메시지엔 참조(키+콘텐츠 해시)만**. 해시를 함께 실으면 소비자 로컬 캐시의 무효화가 공짜로 해결된다(해시 다름=재다운로드). 반복 소비(같은 문제에 제출 N번, batch 재채점)에서 전송량이 참조 크기로 고정되는 게 핵심 이득. 대안들의 실패 모드도 교훈적: 인라인=상한·반복 운반, 소비자가 생산자 API 조회=비동기로 끊은 결합이 동기 HTTP로 뒷문 재입장. **면접 포인트**: "브로커는 이벤트 운반, 대형 데이터는 스토리지 — 각자 잘하는 것만". — 2026-07-26 19:38

### 로드맵이 ADR보다 오래되면 로드맵이 진다
구 로드맵 M1(동기 채점)→M2(Kafka 전환)는 ADR-0006(이음새=Kafka 확정) **이전**의 계획이었다. 전제가 바뀐 뒤에도 로드맵 문자를 따르면 "대체가 이미 결정된 구조물"(동기 HTTP 이음새+타임아웃·백프레셔 처리)을 지었다 버리게 된다. 점진성이 필요하면 **버릴 층(전송)이 아니라 남길 층(코어)을 먼저 만드는 순서**로 확보한다 — judge 코어를 전송 무관하게 선검증하고 Kafka 어댑터를 나중에 붙이면 동기 단계 없이 같은 점진성. (CLAUDE.md 작업 원칙 4 "전제가 죽은 규칙은 규칙이 아니다"의 로드맵 버전) — 2026-07-26 19:38

## 메시징 (Kafka)

### KRaft — ZooKeeper 없는 Kafka
Kafka 4.0에서 ZooKeeper가 **완전 제거** — 메타데이터(토픽·파티션·리더 선출)를 Kafka 자체 Raft 쿼럼(KRaft)이 관리한다. 외부 코디네이터 의존 제거로 운영 단순화 + 컨트롤러 장애 조치 고속화. 개발 환경은 컨테이너 하나가 broker+controller 겸직(combined mode). "Kafka 하면 ZooKeeper"는 이제 구지식. — 2026-07-26 19:38

### advertised.listeners — 도커 Kafka의 대표 함정
Kafka 클라이언트는 부트스트랩 주소로 첫 접속 후, 브로커가 메타데이터로 알려주는 **advertised 주소로 갈아탄다**. 그래서 접속 경로별로 advertise가 맞아야 한다: 호스트 네이티브 앱에 `kafka:29092`를 알려주면 호스트에서 못 찾고, 컨테이너 내부 클라이언트에 `localhost:9092`를 알려주면 자기 자신에 접속한다. 해법 = **리스너 분리**(HOST://localhost:9092 + DOCKER://kafka:29092). "접속은 되는데 이후가 안 된다"면 십중팔구 이것. — 2026-07-26 19:38

### 토픽 자동 생성을 끄는 이유
`auto.create.topics.enable=true`(기본)면 존재하지 않는 토픽에 첫 메시지가 오는 순간 **파티션·보존 설정이 기본값으로** 토픽이 생긴다 — 의도한 파티셔닝·보존 정책과 무관하게 굳어버림. 명시 생성(init 스크립트/IaC)이 운영 규율. QoS 레인처럼 토픽이 계약의 일부면 더더욱. — 2026-07-26 19:38

## 백엔드 (api / Kotlin)

### 코루틴 suspend 컨트롤러 — Reactor 없이 논블로킹
Spring WebFlux에서 핸들러를 `suspend fun`으로 선언하면 Reactor의 `Mono/Flux` 체이닝 없이 **동기 코드처럼 읽히는 논블로킹**이 된다(kotlinx-coroutines-reactor가 다리). 리포지토리는 `CoroutineCrudRepository`로 suspend/Flow를 그대로 받는다. "논블로킹의 성능 + 블로킹의 가독성"이 코루틴 채택의 핵심 논리. — 2026-07-25 14:07

### R2DBC vs JPA — 뭘 포기하고 뭘 얻나
R2DBC는 논블로킹 드라이버지만 JPA의 연관관계 매핑·지연로딩·캐시가 없다 — join 대신 **쿼리 2번 + 코드에서 조합**(problem+examples groupBy)이 관용구. 엔티티는 그냥 행(row) 매핑이다. 이 프로젝트에선 "실무(JPA) 재탕 회피 + WebFlux 스택 일관성"으로 채택(ADR-0007). JSONB는 `io.r2dbc.postgresql.codec.Json` 타입으로 받고 어댑터에서 Map으로 변환, PG 배열은 `List<String>` 자동 매핑. — 2026-07-25 14:07

### 문자 인코딩 3층 — JEP 400, Gradle 포크, 코덱의 기본문자셋 의존
Windows에서만 JSONB 한글이 깨진 버그(`여기에`→`뿬湲곗뿉`, UTF-8 바이트를 CP949로 디코딩한 모지바케)의 해부. 층이 3개다: ① **JDK 18+ (JEP 400)**: `file.encoding` 기본값이 플랫폼 인코딩→UTF-8로 바뀌어 "자바는 이제 어디서나 UTF-8"이라 믿기 쉽지만 ② **Gradle `bootRun`(JavaExec)이 데몬의 네이티브 인코딩(한국어 Windows=MS949)을 `-Dfile.encoding`으로 포크 JVM에 명시 전달**해 그 기본값을 도로 덮는다 ③ 그 위에서 r2dbc `Json.asString()`처럼 **기본문자셋으로 디코딩하는 API**를 쓰면 플랫폼 의존 버그가 된다. TEXT 컬럼은 r2dbc 코덱이 항상 UTF-8이라 무사했고 JSONB만 우리 코드의 `asString()`을 지나서 깨짐 — 같은 응답 안에서 필드별로 증상이 갈린 이유. **수정**: `asString()`→`asArray()`(Jackson은 byte[]를 JSON 스펙대로 UTF-8 해석 — 진짜 수정) + `JavaExec.defaultCharacterEncoding = "UTF-8"`(방어). **교훈**: 인코딩 버그는 "어느 층에서 기본값이 덮였나"를 실측(jcmd `VM.system_properties`)으로 확인할 것 — macOS에서 멀쩡했던 건 고쳐진 게 아니라 네이티브 인코딩이 우연히 UTF-8이었을 뿐(잠재 버그의 은폐). — 2026-07-26 18:59

### Flyway V vs R — 적용된 마이그레이션은 불변이다
`V__`(버전) 마이그레이션은 적용 시 **체크섬이 기록**되고, 이후 파일을 주석 한 글자라도 수정하면 기동이 거부된다(오늘 일괄 리네임 sed로 실제로 밟은 함정 — 변조 감지 기능의 정상 동작). 반면 `R__`(Repeatable)은 파일 내용이 바뀔 때마다 재적용된다 → **스키마=V(불변 이력), 시드·뷰=R(갈아끼움, 멱등 필수)** 가 올바른 역할 분담. 시드를 V로 넣으면 더미데이터 수정이 불가능해진다. — 2026-07-25 16:17

### 스키마의 주인 — 앱 소유 vs DB 소유
"스키마는 DB에 종속되어야 하지 않나?"는 공유 DB+DBA 시대의 모델. 현대 서비스 지향에선 **스키마 = 그 데이터를 소유한 서비스의 도메인 모델** — 마이그레이션이 앱 코드베이스에 살고 앱과 함께 버전업된다(스키마와 코드는 항상 함께 변하므로). 대가는 기동 순서 강제(DB부터). DB 서버(엔진, infra 소관) ≠ 스키마(도메인 지식, 서비스 소관)의 구분이 핵심. — 2026-07-25 16:17

### 이름 짓기 — 2층 체계(책임 영역/처리 단계)
서비스 이름의 세 가지 실패 모드를 겪음: ① 은유(arena·hub) = 위치를 꾸민 것, 정보량 0 ② 행위자 통일(-er: generator·author) = 상위가 하위 일부만 대표 ③ 수단 이름(embedding) = 목적을 못 덮음. 해법: **상위 = 책임 영역**(judge·problem·plagiarism — "무엇을 담당"), **하위 = 처리 단계**(generation→validation→workflow — "어떤 순서"). 층마다 답하는 질문이 달라 포괄 문제가 구조적으로 사라진다. — 2026-07-25 16:17

### Flyway — 기동 시 마이그레이션 + 함정

### 폴리글랏 계약 — OpenAPI codegen + 컴파일타임 드리프트 검출
프론트·백이 다른 언어면 타입 공유가 불가 → **서버가 스펙을 생성**(springdoc `/v3/api-docs`)하고 클라이언트가 **타입을 생성**(openapi-typescript). 여기에 `contract-check.ts`로 "도메인 모델 ↔ 생성 스키마"의 키 집합 일치·타입 호환을 타입 레벨에서 검사하면, 서버가 필드를 개명해도 **프론트 빌드가 실패**해 드리프트를 조기 검출한다. 생성물은 커밋(빌드 재현성). — 2026-07-25 14:07

### JDK LTS 라인과 버전 정책
