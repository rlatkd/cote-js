### AI 플랫폼에서 AI는 런타임 경로에 없다 — 산출물은 데이터로 물화된다

사용자 문답("AI로 만든 문제, 채점은 어떻게?")에서 정리된 원리. 우리 시스템에서 **AI의 역할은 문제가 게시되는 순간 끝난다.** 생성·교차검증을 통과한 산출물은 `test_case` 테이블의 검증된 입출력 쌍으로 **물화(materialize)**되고, 이후 유저 제출 채점은 그 데이터를 상대로 한 100% 결정적 실행-비교다 — 채점 경로에 LLM 호출이 0회. 이 분리가 주는 것: ① 채점의 재현성·신뢰성(같은 코드는 언제나 같은 판정 — LLM이 끼면 불가능) ② 비용·지연 분리(LLM 비용은 생성 시 1회, 제출마다 아님) ③ 장애 분리(LLM API가 죽어도 채점은 무관). 일반화하면: **"AI 기반 서비스"에서 AI를 어디에 두는가의 설계 문제 — 요청 경로(런타임)에 두면 비결정성·비용·장애를 매 요청이 지불하고, 생산 파이프라인(빌드타임)에 두면 산출물 검증 시점에 한 번만 지불한다.** 우리는 채점(정확성이 생명)에선 후자를 강제했고, 유일하게 런타임에 AI가 남는 후보는 M4 유사도 검색(근사 허용 영역)이다. — 2026-08-01 12:52

### 오판정은 0이 될 수 없다 — 채점 신뢰성은 "항상 옳음"이 아니라 "교정 가능성"으로 설계한다

사용자 문답("옳게 풀었는데 오답 처리될 수 있지 않나")에서 정리. **맞는 풀이가 오답(false negative) 처리되는 경로는 3계층**이고, 층마다 방어가 다르다:

1. **문제 자체가 틀림** (AI 생성에서 최대 리스크) — ① 테스트케이스 정답이 틀림(N개 합의가 공통 오개념으로 뚫린 경우) ② **복수 정답인데 유일 출력을 가정**(정답인데 기대 출력과 다름) ③ 지문 모호(다른 합리적 해석으로 풂). 방어: 교차검증 — 특히 **복수 정답 문제는 독립 풀이들의 출력이 갈리므로 검증 단계에서 자동 반려되는 부수 효과**가 있다(합의 검증이 special judge 필요 문제를 걸러주는 필터를 겸함). 잔여 위험은 공통 오개념뿐.
2. **비교 규칙이 틀림** — 공백·개행 정규화는 있으나, 부동소수점 표기(0.5 vs 0.50)·형식 허용 폭 같은 것은 유일 출력 범위 제한으로 회피 중. 범위를 넓히는 순간 special judge가 필요해진다.
3. **실행 환경이 틀림** — **TLE가 가장 취약**: 시간은 결정적 값이 아니라 **기계 상태에 의존하는 측정값**이다(동시 슬롯 2의 noisy neighbor, JIT 웜업, 디스크 캐시). 언어별 시간 배수로 체계 편차는 보정하지만 순간 부하 편차는 남는다 — 실제 저지들도 TLE 경계는 고질이라 제한을 정답 풀이 실측의 2~3배로 여유 있게 잡는 관행.

**일반 원리**: 위 3층을 다 막아도 오판정 확률은 0이 아니다. 따라서 채점 시스템의 신뢰성은 "판정이 항상 옳다"가 아니라 **"틀린 판정을 발견하고 교정할 수 있다"**로 설계한다: ① 케이스별 결과 투명 공개(유저가 이상함을 감지할 수 있게 — 이미 있음) ② 재채점 경로(멱등 저장+재채점 시 케이스 대체가 이미 인프라로 존재, 문제 결함 발견 시 케이스 수정 후 batch 레인으로 전 제출 일괄 재채점) ③ 이의제기 채널(미구축 — admin 백로그). 오판정 대응이 설계에 들어있는 저지와 아닌 저지의 차이는 결함 발생 시 드러난다. — 2026-08-01 12:55

### 기존 저지가 "잘" 채점하는 이유 — 엔진이 아니라 프로세스와 군중

사용자 문답("기존 코딩테스트 사이트는 어떻게 그렇게 잘 채점하나")에서 정리. 그들의 실행-비교 엔진은 우리와 본질적으로 같다(샌드박스 실행→출력 비교). 차이는 4가지 층위:

1. **출제 프로세스(사전)** — Codeforces Polygon이 전형: 문제마다 입력 validator·checker(special judge)·**의도 풀이+brute-force+일부러 틀린 풀이 여러 벌**을 요구하고, 라운드 전 테스터들이 독립적으로 푼다. ICPC도 저지 풀이를 복수 언어로 준비해 교차 확인. **우리 M3 교차검증 파이프라인은 이 사람-프로세스의 자동화판**이다(N개 독립 풀이=테스터, brute-force 앵커=저지 풀이 대조).
2. **군중 = 상시 오류 탐지 시스템(사후)** — 수만~수백만 제출이 지속 검증 역할. 백준의 "데이터 추가" 제보→반영→**전체 재채점** 문화, Codeforces의 핵(hack — 남의 AC 풀이를 반례로 깨뜨리기, 성공하면 그 반례가 데이터에 추가됨). 즉 "잘 맞는다"는 인상은 상당 부분 **수년간 두들겨 맞고 교정된 결과(생존 편향)**다. 지금도 재채점 공지는 일상이다.
3. **시간 판정 운영 성숙** — 전용 동일 사양 채점 머신, 머신당 1제출(noisy neighbor 원천 제거), 제한=의도 풀이의 2~3배, 언어 배수, 일부는 복수 실행 후 최솟값. 그래도 LeetCode 경계 TLE 악명처럼 완벽하지 않다.
4. **checker 도구 성숙** — testlib 같은 수십 년 축적된 special judge 라이브러리로 복수 정답·허용 오차를 다룬다(우리는 범위 제한으로 회피 중인 영역).

**시사점**: 우리 설계는 1(교차검증)·재채점 인프라(2의 교정 루프)를 이미 닮게 만들었고, **작은 서비스가 못 가지는 건 2의 군중**이다 → 그만큼 사전 검증과 사람 검수 게이트의 비중이 커야 한다. 일반 원리: **채점 품질은 엔진 성능이 아니라 [사전 프로세스 × 사후 교정 루프]의 곱이다.** — 2026-08-01 12:57

### 축적의 세 형태 — 도구·지식은 이식되지만, 독립적 다양성은 근사만 된다

사용자 문답("수년간의 축적을 지금 기술로 압축할 수 없나")에서 정리. 기존 저지의 축적을 분해하면 세 형태고, 기술(LLM)이 압축할 수 있는 정도가 다르다:

1. **도구(코드) — 그대로 이식 가능.** testlib 등 checker/validator는 오픈소스이고 패턴도 공개돼 있다. 수십 년 축적이지만 지금 당장 가져다 쓸 수 있는 형태.
2. **지식(프로세스) — 이식 + 자동화 가능. 여기가 LLM의 최대 지렛대.** Polygon식 출제 관행(복수 저지 풀이·validator·stress testing)은 문서화된 공개 지식이고, 우리 M3 교차검증은 이미 그 인코딩이다. 과거에 사람 테스터 여러 명·수 주가 들던 **노동**을 LLM이 분 단위로 압축한다 — "기술이 몇 배 발전했다"가 실제로 현금화되는 지점.
3. **정보(군중의 탐색) — 압축 불가, 근사만 가능.** 수백만 제출은 지식이 아니라 **다양한 인간들이 문제 공간을 독립적으로 두들긴 표본**이다. LLM N개 풀이는 군중의 시뮬레이션이지만 **오류가 상관**돼 있다(비슷한 모델은 같은 오개념을 공유 — 상관된 앙상블은 교정력이 제한적). 인간 군중의 힘은 규모가 아니라 **탈상관(decorrelation)**에 있다.

**3의 근사 수단(격차를 좁히는 것)**: ① stress testing — 랜덤+적대적 입력 대량 생성 후 brute-force와 최적 풀이 대조(혼자 출제하는 경쟁 프로그래머들이 쓰는 검증법 = 이미 기계화된 군중 대체물) ② **적대적 반례 탐색** — "이 문제/풀이를 깨뜨릴 입력을 찾아라"는 핵(hack) 문화의 자동화 ③ **모델 다변화** — 독립 풀이를 서로 다른 모델 계열로 생성해 오류 탈상관. 이걸 다 해도 남는 것: 기묘하지만 그럴듯한 오해석의 롱테일, 경계선 TLE — 그래서 교정 루프(재채점)와 사람 게이트는 여전히 필요하다. **일반 원리: 기술은 노동과 지식을 압축하지만, 독립적 다양성이라는 정보는 생성할 수 없고 근사할 수 있을 뿐이다.** — 2026-08-01 12:59

### 파인튜닝은 다양성을 만들지 않는다 — 그리고 학습은 축적을 소비한다

사용자 문답("로컬 LLM에 학습시키면 되지 않나")에서 정리. 앞선 '축적의 세 형태'의 연장 — 탈상관 격차를 파인튜닝으로 메울 수 있는가에 대한 두 원리:

1. **파인튜닝은 분포를 좁히는 작업이지 넓히는 작업이 아니다.** 특정 태스크에 맞춰 출력을 수렴시키는 게 파인튜닝의 정의라, 오류의 탈상관(서로 다르게 틀리기)을 만들어내지 못한다. 오히려 악화 요인도 있다 — 오픈 모델 다수가 프론티어 모델 출력을 증류해 학습하므로, "다른 모델"처럼 보여도 오류 계보가 같다. 앙상블 다양성은 학습으로 제조하는 게 아니라 **기원이 다른 모델을 고르는 것**으로만 얻는다.
2. **학습은 축적의 대체가 아니라 소비다.** 파인튜닝에는 학습 데이터가 필요한데, 그 데이터가 바로 우리가 없다던 축적이다(군중의 제출·교정 이력). 축적이 없어서 학습으로 대체하려는데 학습이 축적을 요구하는 순환. 외부 문제·풀이 코퍼스로 학습하는 건 라이선스 논의로 회귀(학습 이용은 재배포보다 회색이지만 리스크 0 아님).
3. (부가) **검증 신호의 질은 풀이자의 능력에 상한된다.** 교차검증에서 "불일치=문제 결함"이라는 추론은 풀이자가 충분히 강할 때만 성립한다. 로컬 모델의 추론 격차가 크면 불일치가 "풀이자가 못 풀었다"는 노이즈가 되어, 어려운 문제일수록 파이프라인이 판별력을 잃는다 — 검증자는 생성자만큼 강해야 한다.

**우리 결론**: 문제 생성·검증 = 프론티어 API 유지(ADR-0001의 파인튜닝 배제 재확인 — 이번엔 탈상관 관점에서도). "직접 학습"이 설 자리는 이미 설계에 있다 — **M4 자체 Sentence Transformer**(유사도는 근사 허용 영역 + 도메인 특화 파인튜닝이 정당한 자리). 로컬 LLM의 잔여 후보는 앙상블 다변화의 한 멤버 정도(능력 하한 조건부). — 2026-08-01 13:05

### SSE vs WebSocket — 채점 알림엔 왜 SSE인가

**문제 정의부터**: 채점을 비동기(Kafka)로 만든 순간 "제출 API는 접수만 응답하고, 판정은 몇 초 뒤 도착한다"가 된다. 그래서 **"web은 결과가 나온 걸 어떻게 아는가"**라는 문제가 새로 생긴다. 이건 비동기화가 낳은 필연적 숙제지 별개 기능이 아니다.

**선택지는 셋**: ① 폴링(web이 주기적으로 물어봄) ② SSE ③ WebSocket.

| 축 | 폴링 | SSE | WebSocket |
|---|---|---|---|
| 방향 | 단방향(요청 기반) | 서버→클라 단방향 | 양방향 |
| 프로토콜 | 일반 HTTP | 일반 HTTP(`text/event-stream`) | HTTP 업그레이드 후 별도 프레이밍 |
| 재연결 | 해당 없음 | **브라우저 내장**(자동 재시도 + `Last-Event-ID`) | 직접 구현 |
| 인프라 궁합 | 최상 | 상(HTTP라 프록시·인증 그대로) | 중(프록시·LB가 업그레이드 지원 필요) |
| 비용 | 결과 없을 때도 계속 요청 | 연결 1개 유지 | 연결 1개 유지 |

**판단**: 채점 알림은 **서버→클라이언트 단방향**이다. WebSocket의 양방향성은 이 요구에 쓰이지 않는데 비용(핸드셰이크 업그레이드, 재연결 직접 구현, 프록시·LB 설정, 별도 인증 경로)은 전부 낸다 — **쓰지 않을 능력에 값을 치르는 것**이 오버엔지니어링의 정의. SSE는 일반 HTTP라 기존 인증·프록시·관측이 그대로 먹고, 재연결이 브라우저에 내장돼 있다. WebFlux에선 `Flow<ServerSentEvent>` 반환이면 끝이라 구현도 작다.

**폴링을 배제한 이유**: 만들기는 제일 쉽지만 두 번 만들게 된다 — 나중에 SSE로 가면 폴링 코드는 폐기물. (동기 채점을 건너뛴 것과 같은 논리)

**언제 뒤집히나 (조건을 적어두는 게 중요)**: ① 클라→서버 실시간 입력이 생길 때(라이브 코딩 협업·대회 중 실시간 채팅) ② 바이너리 프레임이 필요할 때 ③ 한 브라우저에서 HTTP/1.1로 6+ 동시 스트림이 필요할 때(도메인당 연결 상한 — HTTP/2면 해소). 지금은 셋 다 아니다.

### IDL 선택 — Protobuf vs Avro는 "무엇을 지키려는가"가 다르다
둘 다 스키마 기반 이진 직렬화지만 강조점이 다르다. **Avro**는 Kafka 생태계와 Schema Registry를 전제로 **스키마 진화의 강제**(subject별 backward/forward 호환성 검사)에 강하고, 메시지에 스키마 id만 싣는다. **Protobuf**는 언어 중립 코드젠의 범용 표준으로, 진화 규칙(필드 번호 불변·`reserved`)을 **개발자 규율**로 지킨다. 즉 Avro는 "레지스트리가 막아준다", Protobuf는 "규칙을 지켜야 한다". 이 프로젝트가 Protobuf를 택한 결정타는 성능·크기가 아니라 **경계의 개수**였다 — 지킬 경계가 api↔judge 하나면 Avro+Registry가 정석이지만, M3의 api↔AI(Python)까지 있어서 **경계마다 도구를 갈아타지 않는 단일 IDL**의 정합성이 이겼다. Registry는 Protobuf도 지원하므로 거버넌스가 필요해지면 IDL 교체 없이 층만 추가할 수 있다는 점(배타적 선택이 아님)도 판단 근거. **면접 포인트**: "선택지가 배타적인지부터 확인한다 — 나중에 얹을 수 있으면 지금 미루는 게 옳다." — 2026-07-26 20:05

CI의 web 잡이 `pnpm/action-setup`에서 죽었다(`No pnpm version is specified`). 해결책은 두 가지였다: ① 워크플로에 `version: 10.33.0`을 적는다 ② `package.json`에 `packageManager` 필드를 둔다. **②를 택한 이유는 진실원의 개수**다 — ①은 로컬(개발자 pnpm)과 CI(워크플로)에 버전이 **두 곳**에 생겨 어긋날 수 있고, 어긋나면 "로컬에선 되는데 CI에서 안 되는" 전형적 문제가 된다. ②는 로컬 corepack과 CI가 **같은 한 곳**을 읽는다. **일반화**: 버전·설정을 CI에 하드코딩하기 전에 "프로젝트 자체가 이미 그 정보를 갖고 있지 않은가"를 먼저 본다. 부수 확인 사항으로 같은 유형의 함정 하나 더 — 리눅스 러너에서 `gradlew`의 실행 권한 비트(git mode 100755)가 없으면 Permission denied가 난다(우리는 이미 설정돼 있었다). — 2026-07-28 22:05

### 초록불은 "검사가 실행됐다"는 뜻이 아니다
CI 잡 3개가 통과했지만 검토해보니 **`buf breaking`은 한 번도 실행된 적이 없었다** — `if: github.event_name == 'pull_request'` 조건이 걸려 있는데 이 저장소는 main 직접 푸시가 주 흐름이었다(머지 커밋 0개). 스키마 호환성 강제 장치를 세워두고 **꺼진 줄도 모르고 있었던** 셈이다. **교훈**: 조건부 스텝은 "그 조건이 우리 실제 워크플로에서 성립하는가"를 확인해야 한다. 검사를 추가한 뒤에는 **일부러 위반을 만들어 빨간불이 뜨는지** 확인하는 것이 유일하게 확실한 검증이다(우리는 proto에 필드를 추가해 재생성 없이 검사를 돌려 드리프트 감지를 확인했다). — 2026-07-28 22:10

### 줄바꿈은 개발 OS와 CI OS가 다를 때 조용히 터진다
저장소 blob에 CRLF가 담겨 있으면 리눅스 CI에서 ① 코드 생성 결과가 매번 달라 보이고(생성물 드리프트 검사가 100% 오탐) ② 셸 스크립트가 캐리지리턴 때문에 실행 실패한다. 근본 해결은 `.gitattributes`의 `* text=auto eol=lf`로 **저장소에는 항상 LF**를 담는 것(Windows 작업 트리는 CRLF로 체크아웃해도 무방). 이미 `gradlew`에 `text eol=lf`가 붙어 있던 것도 같은 이유였는데, 규칙이 파일 하나에만 있어 전체로 확장되지 않은 상태였다. **교훈**: 크로스 OS 프로젝트에서 줄바꿈은 "나중에 정리할 스타일 문제"가 아니라 **빌드 재현성 문제**다. — 2026-07-28 22:10

### CI에 넣지 **않을** 것을 정하는 게 CI 설계다
CI에 전부 넣으면 느려지고 flaky가 섞여 "빨간불 무시" 문화가 생긴다. 우리 기준: **빠르고 결정적인 것만**(단위·계약 검사·빌드·핵심 불변식 통합). 제외한 것은 샌드박스 실채점(러너 이미지 3종 빌드 + 시간 측정이 머신 부하에 민감)과 전 구간 E2E(인프라 4종 — 실패 원인이 코드인지 환경인지 흐려짐). 제외한 것은 버리는 게 아니라 **수동 절차로 명시해 남긴다.** — 2026-07-28 21:57

## 서비스 간 계약 (폴리글랏)

### 라이선스 없는 공개 저장소는 "열린 것"이 아니라 **전권 유보**다
저작권은 등록·표시 없이 창작 순간 자동 발생하므로(베른 협약) 아무 말도 안 하면 **모든 권리가 저작자에게** 남는다. 라이선스는 "쓰지 마"를 푸는 게 아니라 **애초에 없던 허락을 부여**하는 문서다. 그래서 public 저장소라도 라이선스가 없으면 포크·수정·재배포가 전부 불가하고, 기업 OSS 정책은 예외 없이 "라이선스 미표기 = 사용 금지"다. GitHub ToS가 예외로 허용하는 건 **GitHub 안에서의 열람·포크**까지뿐. 두 가지가 특히 실무적이다: ① 라이선스에는 **면책**(무보증·책임 제한)이 딸려 오므로 없으면 저작자 보호 장치도 없다 ② **부착 비용은 기여자가 생기는 순간 뛴다** — 나중에 붙이려면 전 기여자의 동의가 필요하고 한 명이라도 연락이 끊기면 그 코드를 들어내야 한다(대형 프로젝트가 CLA를 받는 이유). 1인 프로젝트일 때가 가장 싸다. 그리고 MIT는 배포된 스냅샷에 대해 **철회 불가**라, 권리가 불분명한 자산(외부 파생 데이터 등)이 섞여 있으면 붙이기 전에 걷어내야 한다. — 2026-08-06 22:30

### ACL · Published Language · Shared Kernel — "공통 관심사"에는 이름이 있다
서로 다른 서비스가 시간·실패·식별자 같은 공통 개념을 어떻게 맞출 것인가는 DDD 컨텍스트 매핑의 세 어휘로 갈린다: **ACL**(각자 번역 — "서버별 컨버터"), **Published Language**(교환용 공통 스키마), **Shared Kernel**(공통 모델을 함께 소유 — 사내 공통 라이브러리). 핵심 판단: **공표 언어가 있으면 컨버터가 얇아지고, 없으면 N×N 번역이 된다.** 서비스 3개는 ACL만으로 감당되지만 5개가 되면 해석이 갈라진다. 그리고 **수단은 스택 동질성에 따라 달라진다** — 단일 스택이면 사내 공통 라이브러리가 최적해지만, 폴리글랏이면 언어 수만큼 라이브러리를 유지해야 해서 무게중심이 **코드젠·사이드카·플랫폼**으로 이동한다. — 2026-07-28 21:35

### 강제 지점은 관심사의 종류에 따라 다르다
"공통 규약을 시스템으로 강제한다"는 하나의 방법이 아니라 **층이 다른 여러 방법**이다: **값·메시지의 의미**(시간·금액·식별자) → IDL + 코드젠 / **통신 동작**(재시도·타임아웃·mTLS·트레이스 전파) → 사이드카·서비스 메시 / **서비스 내부 규율**(어떤 타입으로 저장하나) → lint·CI 게이트. **서비스 메시는 페이로드의 의미를 못 잡고, 코드젠은 서비스 내부를 못 잡는다.** 그래서 "메시를 깔면 해결된다"도, "스키마만 있으면 된다"도 틀렸다. 규모에 따른 선택도 중요 — 서비스 3개에 메시는 과설계이고, 그 자리를 대신하는 가장 값싼 수단이 **CI 게이트**다. — 2026-07-28 21:35

### 실패는 "무엇이 일어났나"가 아니라 "받는 쪽이 무엇을 해야 하나"로 표현한다
실패를 문자열 하나로 보내면 수신자가 **재시도할지·사용자에게 보일지·운영자를 부를지를 추측**해야 하고, 추측이 서비스마다 달라지면 같은 실패가 다르게 처리된다. 그래서 계약에 판단 재료를 담는다: `origin`(누구 귀책 — 호출자 vs 처리자), `retryable`(재시도 가능 여부 — **발신자만 아는 정보**), `code`(문구가 바뀌어도 불변인 분기 키). 부수 원칙: **정상 판정은 실패가 아니다** — 오답·시간초과는 채점이 성공한 결과이므로 failure를 비운다. "실패"와 "원하지 않는 결과"를 구분하지 못하면 알림이 노이즈가 된다. — 2026-07-28 21:35

### 필드 교체는 3단계(추가 → 병행 → 제거)를 거친다
발행자와 소비자가 다른 서비스면 **동시에 배포되지 않는다.** 필드를 바로 바꾸면 아직 옛 필드를 읽는 소비자가 깨진다. 그래서 새 필드를 추가하고, 전환 기간 동안 **둘 다 채우고**, 소비자 전환이 끝난 뒤 제거한다. 이 규율을 사람이 기억하는 대신 `buf breaking` 같은 도구가 검사하게 하는 것이 스키마 거버넌스의 최소 형태다. — 2026-07-28 21:35

### 동일성은 원문 없이 해시로 계약할 수 있다 — 단, "요구가 동일성인지 내용인지"를 먼저 물어라
problem의 합의 검증은 풀이들의 출력이 **서로 같은지 / 초안 기대와 같은지**만 필요하고 출력 원문은 필요 없다. 그래서 judge 결과에 원문 대신 **정규화 출력의 sha256**(`CaseResult.output_sha256`)을 실었다 — 크기·노출 문제 없이 동일성 비교가 성립한다. 성립 조건 둘: ① **정규화 규칙을 발신·수신이 공유**해야 한다(같은 바이트가 아니라 같은 의미의 출력이 같은 해시가 되게 — CRLF·후행 공백 차이가 해시를 갈라놓으면 계약이 무너진다) ② 발신 측 해시는 **판정과 같은 코드 경로**에서 계산해야 한다(판정은 AC인데 해시는 다른, 어긋난 두 진실이 못 생기게). 한계도 명확하다: 소비자가 **내용**을 원하면(히든 케이스 생성 — 합의 출력을 정답으로 채택) 해시로는 부족하다. 그때는 원문의 claim-check가 필요 — 요구를 동일성으로 좁힐 수 있는 동안만 해시가 정답이다. — 2026-08-03 21:10 ([ADR-0023](decisions/0023-problem-kafka-wiring.md))

### id 공간 분할 — 계약 변경 없이 트래픽 클래스를 공존시키는 가장 싼 방법
검증 제출(problem)과 유저 제출(api)은 같은 계약(`judge/v1.Submission`)을 타지만 결과의 주인이 다르다. 전용 응답 토픽·타입 필드 추가 대신 **id 공간을 부호로 분할**했다(코어 DB 시퀀스=양수, 검증 트래픽=음수 난수). 성립 조건: 수신자들이 이미 "미지 id는 스킵"하는 규율을 갖고 있어야 한다(api 결과 컨슈머의 기존 IT). 계약 표면이 늘지 않고, 잘못 섞여도 구조적으로 충돌 불가(부호가 다르니까). 단 이건 **암묵이 되기 쉬운 규약**이라 계약 주석에 명시했다 — id 공간 분할은 문서화 없이는 다음 사람에게 지뢰다. — 2026-08-03 21:10

## 채점 시스템 (judge / Go)

### 자원 한도는 런타임마다 강제 수단이 다르다
메모리 한도를 "모든 언어에 동일하게" 걸 수 없다는 것이 실측으로 드러났다. Python은 `RLIMIT_AS`(주소공간 상한)로 걸면 `MemoryError`를 내며 정확히 죽지만, **JVM·V8은 힙과 무관하게 가상주소를 크게 예약**해서 같은 방식을 쓰면 **정상 코드도 기동조차 못 한다** → `-Xmx`·`--max-old-space-size` 같은 **런타임 자체의 힙 옵션**을 써야 한다. 시간도 마찬가지로 런타임 기동 비용이 달라 배수 보정이 필요하다(문제의 제한값은 통상 C/C++ 기준). **교훈**: "언어 추가 = 러너 하나 추가"가 되려면 언어별로 다른 것이 무엇인지 먼저 목록화해야 한다 — 이미지·소스명·실행명령뿐 아니라 **자원 강제 방식과 실패 시그니처**까지. — 2026-07-28 21:35

### 인터프리터 언어에도 "컴파일 단계"를 주면 얻는 것
컴파일이 없는 언어(Python·JS)에 문법 검사(`py_compile`·`node --check`)를 컴파일 단계로 넣으면, 문법 오류가 **케이스마다 런타임 에러로 반복 보고되는 대신 `COMPILE_ERROR`로 한 번에** 나온다. 사용자에게 정확한 정보(문법 오류지 로직 오류가 아님)이고 케이스 실행도 낭비하지 않는다. **일반화**: 인터페이스의 단계 이름("컴파일")에 갇히지 말고 그 단계의 **역할**("실행 전 검증")로 생각하면, 그 역할이 필요한 다른 대상에도 자리를 내줄 수 있다. — 2026-07-28 21:35

### 인터페이스는 "변할 것과 변하지 않을 것 사이"에 긋는다
judge에서 확실히 바뀔 것은 **격리 방식**(Docker 옵션 → 커널 직접 제어)이고, 바뀌지 않을 것은 **채점 절차**(케이스 순회·출력 비교·판정 집계)다. 그래서 포트(`Runner`)를 정확히 그 사이에 뒀다 — 2단계 전환이 어댑터 추가로 끝나고 executor는 불변. 반대로 **잘못 그을 뻔한 경계**: "언어별 executor". 언어가 달라도 절차는 같고 실행 방법만 다르므로, 언어를 절차 층으로 올렸다면 언어 추가마다 절차가 복제됐을 것이다. **교훈**: 경계는 "개념이 다른 곳"이 아니라 **"변화 속도가 다른 곳"**에 긋는다. — 2026-07-26 20:05

### 유저 귀책과 시스템 장애를 타입으로 분리하라
채점에서 "코드가 틀렸다"와 "채점기가 고장났다"는 완전히 다른 사건인데, 코드로는 둘 다 "실패"라 뭉개지기 쉽다. 규율: **Go의 `error`는 시스템 장애에만, 유저 귀책은 `Verdict`로.** 그래서 `Compile()`은 컴파일 실패 시 error를 반환하지 않는다(정상 동작이므로) — 시그니처 자체가 정책을 강제한다. `INTERNAL_ERROR`를 별도 판정으로 둔 이유도 같다: 샌드박스 기동 실패를 RE로 뭉뚱그리면 **사용자는 멀쩡한 자기 코드를 의심하고, 운영자는 장애를 못 본다.** 관측 가능성은 판정 체계 설계에서 시작한다. — 2026-07-26 20:05

### 측정하는 자와 판단하는 자를 분리 (harness는 사실만 보고)
컨테이너 안 harness는 `exit_code`·`timed_out`·시간·메모리라는 **관측 사실만** 내놓고, Verdict 번역은 Go executor가 한다. 언어가 늘면 이 분리의 값이 드러난다 — "exit code 1"의 의미는 언어마다 다르고, 판정 정책(MLE를 RE로 볼지 등)은 채점 도메인의 결정이지 실행기의 결정이 아니다. 번역 지점을 한 곳에 모으면 언어가 늘어도 정책이 흩어지지 않는다. 부수 규칙: **판정 우선순위(TLE > MLE > RE > AC/WA)** — 시간 초과로 죽은 프로세스는 exit code도 비정상이라, 순서를 잘못 두면 TLE가 RE로 오분류된다. — 2026-07-26 20:05

### 자원 한도는 "누가 죽어야 하는가"를 설계하는 일
컨테이너 `--memory`만 걸면 초과 시 커널 OOM killer가 프로세스를 죽이는데 **그게 harness일 수도 있다** — 컨테이너째 죽어 결과를 못 받으면 유저 코드의 MLE가 시스템 장애로 둔갑한다. 그래서 두 겹으로 설계: **정밀 한도는 제출 프로세스에만 `RLIMIT_AS`**로 걸어 Python이 `MemoryError`로 스스로 죽게 하고, **컨테이너 한도는 +여유를 둬 harness 생존을 보장하는 backstop**으로. 덤: `--memory-swap`을 `--memory`와 같은 값으로 줘야 스왑으로 한도를 우회하지 못한다. **교훈**: 한도를 건다 = 상한을 정한다가 아니라, **초과 시 누가 어떤 순서로 죽는지를 정한다.** — 2026-07-26 20:05

### `exec.CommandContext`는 컨테이너를 죽이지 않는다
Go에서 컨텍스트 만료 시 죽는 것은 **`docker` CLI 프로세스뿐**이다. 실제 컨테이너는 데몬이 띄운 별개 프로세스라 살아남아 CPU를 계속 태운다("타임아웃을 걸었는데 서버가 느려진다"의 정체). 그래서 컨테이너에 이름을 붙여 두고 예산 초과 시 `docker kill <name>`을 명시 호출한다. **일반화**: 클라이언트-데몬 모델(Docker·systemd·K8s)에서는 **내가 띄운 프로세스를 죽이는 것 ≠ 내가 시킨 작업을 죽이는 것**. 취소는 작업 식별자로 해야 한다. — 2026-07-26 20:05

### 격리 비용과 실익 — 컨테이너를 케이스마다 띄우지 않은 이유
케이스당 컨테이너면 격리는 깨끗하지만 기동 비용(수백 ms)이 케이스 수만큼 곱해진다(100케이스면 실행보다 기동이 압도). 그래서 **컨테이너 1개 + 케이스마다 새 프로세스**(`RLIMIT_AS` 재적용)로 갔다. 근거는 위협 모델: 제출 1건은 코드가 하나라 **케이스끼리 서로를 오염시킬 동기가 없다** — 격리해야 할 경계는 케이스 사이가 아니라 제출과 호스트 사이다. **교훈**: 격리 수준은 "최대한 강하게"가 아니라 **위협 모델이 요구하는 경계**에 맞춘다. — 2026-07-26 20:05

### 출력 비교 — 완전 일치와 전체 무시 사이
byte-exact 비교는 `print()`의 개행 하나로 정답을 오답으로 만들고, 모든 공백 무시는 출력 형식이 의미 있는 문제(행렬·표)에서 오답을 통과시킨다. 표준 저지의 관행은 중간 — ① CRLF→LF ② 줄별 후행 공백 제거 ③ 마지막 빈 줄 무시. **줄 구조는 지키되 눈에 안 보이는 차이는 봐준다.** 채점 시스템에서 "관대함"은 인심이 아니라 **정확도 설계**다(거짓 오답과 거짓 정답 중 무엇을 더 싫어하는가). — 2026-07-26 20:05

### 첫 실패에서 멈출 것인가 — 제품 성격이 정한다
대회용 저지는 첫 오답에서 즉시 중단한다(자원 절약, 순위만 필요). 이 프로젝트는 **끝까지 돌고 케이스별 결과를 전부 남긴다** — 학습 플랫폼이라 "몇 번 케이스에서 왜 틀렸나"가 사용자 가치이고, batch 레인(AI 문제 검증)에서 케이스별 분포 자체가 검증 신호이기 때문. 종합 판정만 첫 실패 케이스의 것으로 정한다. **교훈**: 같은 도메인(온라인 저지)이라도 **제품이 파는 가치**가 알고리즘을 바꾼다. — 2026-07-26 20:05

### 실행 환경의 소유권 — 러너 이미지는 왜 infra가 아닌가
DB·브로커는 여러 서비스가 공유하는 실행 기반이라 infra 소관이지만, **언어 러너 이미지는 judge 소유**다. 근거: 같은 코드가 Python 3.11에서 통과하고 3.13에서 실패할 수 있다 — **어떤 인터프리터로 채점하느냐가 판정의 일부**다. 판정에 영향을 주는 것은 채점 서비스가 소유해야 재현성과 책임 소재가 맞는다(단일 작성자 원칙의 연장). — 2026-07-26 20:05

## 메시징 (Kafka)

### KRaft — ZooKeeper 없는 Kafka
Kafka 4.0에서 ZooKeeper가 **완전 제거** — 메타데이터(토픽·파티션·리더 선출)를 Kafka 자체 Raft 쿼럼(KRaft)이 관리한다. 외부 코디네이터 의존 제거로 운영 단순화 + 컨트롤러 장애 조치 고속화. 개발 환경은 컨테이너 하나가 broker+controller 겸직(combined mode). "Kafka 하면 ZooKeeper"는 이제 구지식. — 2026-07-26 19:38

### advertised.listeners — 도커 Kafka의 대표 함정
Kafka 클라이언트는 부트스트랩 주소로 첫 접속 후, 브로커가 메타데이터로 알려주는 **advertised 주소로 갈아탄다**. 그래서 접속 경로별로 advertise가 맞아야 한다: 호스트 네이티브 앱에 `kafka:29092`를 알려주면 호스트에서 못 찾고, 컨테이너 내부 클라이언트에 `localhost:9092`를 알려주면 자기 자신에 접속한다. 해법 = **리스너 분리**(HOST://localhost:9092 + DOCKER://kafka:29092). "접속은 되는데 이후가 안 된다"면 십중팔구 이것. — 2026-07-26 19:38

### at-least-once vs at-most-once — 오프셋 커밋 시점이 곧 전달 보장이다
Kafka의 전달 보장은 설정 이름이 아니라 **"언제 커밋하느냐"**가 정한다. 커밋을 처리 **전**에 하면 at-most-once(처리 중 죽으면 유실), 처리 **후**에 하면 at-least-once(죽으면 재처리=중복). 채점에서는 **유실이 중복보다 훨씬 나쁘다** — 유실은 사용자 화면이 영원히 "채점 중"에 머무는 눈에 보이는 실패이고, 중복은 채점이 순수 함수에 가까워(같은 코드·케이스 → 같은 판정) 결과가 같다. 그래서 자동 커밋을 끄고 채점 후 수동 커밋. 중복 제거는 소비자(api)가 `submission_id` 멱등 저장으로 흡수한다. **exactly-once를 배제한 이유**: Kafka 트랜잭션은 브로커 내부의 원자성일 뿐, 우리 부수효과는 외부(Docker 컨테이너 실행)에 있어 롤백되지 않는다 — 비용은 큰데 보장은 불완전. **면접 포인트**: "전달 보장은 인프라 설정이 아니라 **실패 시 무엇을 감당할지**의 선택." — 2026-07-26 20:30

### 멱등 소비자가 있어야 at-least-once가 완성된다
at-least-once는 "중복이 올 수 있다"를 시스템 전체가 받아들이는 계약이다. 생산 측만 바꾸고 소비 측이 그대로면 중복 저장·중복 알림으로 터진다. 그래서 두 장치를 세트로 둔다: ① **자연 키로 멱등 저장**(`submission_id` upsert) ② **결과 토픽 키 = `submission_id`** — 같은 제출의 결과가 같은 파티션에 들어가 순서가 보장된다(파티션 간에는 순서 보장이 없다는 점이 자주 잊힌다). — 2026-07-26 20:30

### poison message — 재시도하면 안 되는 실패도 있다
역직렬화 실패처럼 **재시도해도 결과가 같은 실패**를 무한 재시도하면 그 파티션이 영구히 막힌다(뒤 메시지가 전부 굶음). 그래서 "재시도 가능한 실패(네트워크·일시적 장애)"와 "재시도 불가능한 실패(형식 오류)"를 구분해 후자는 로그만 남기고 건너뛴다. 운영 단계에서는 버리는 대신 DLQ(dead letter queue)로 보내 사후 분석한다. — 2026-07-26 20:30

### 캐시 무효화를 콘텐츠 해시로 없애기
"캐시 무효화가 컴퓨터 과학의 두 난제 중 하나"인 이유는 **언제 낡았는지 알아내야** 하기 때문이다. 캐시 키를 경로가 아니라 **콘텐츠 해시**로 잡으면 그 문제가 사라진다 — 내용이 바뀌면 키가 달라지므로 자동으로 미스가 나고, 무효화 로직 자체가 필요 없다(내용 주소 지정, content-addressable). Git·Docker 레이어·Nix가 다 이 방식. 부수 규칙 둘: ① **완료 마커**가 있어야 한다 — 디렉토리 존재만 보면 다운로드 중 죽은 반쪽 캐시를 유효로 오인한다 ② **staging → rename**으로 원자적 게시(완성된 것만 캐시 경로에 나타나게). — 2026-07-26 20:30

### zip slip — 아카이브의 경로를 신뢰하지 말 것
tar/zip 엔트리 이름에 `../../etc/passwd` 같은 경로가 들어 있으면, 순진하게 `filepath.Join(dest, name)`으로 풀 때 **압축 해제 디렉토리 밖에 파일을 쓴다**(zip slip). 방어는 두 줄: 정규화 후 목적지 경로가 여전히 dest 하위인지 검사, 심볼릭 링크 엔트리는 무시(링크로도 탈출 가능). 우리 번들은 내부 발행물이지만, **신뢰 경계 안이라도 형식 검증은 한다** — 나중에 problem 서비스가 생성한 번들이 같은 경로로 들어온다. — 2026-07-26 20:30

### 우선순위 큐가 아니라 "폴 배치 내 정렬"로 QoS를 구현한 이유
Kafka에는 우선순위 토픽이 없다. 흔한 구현은 ① 레인별 전용 워커 풀 ② 단일 워커가 여러 토픽을 구독하고 **한 폴에서 받은 레코드를 우선순위로 정렬**. ②를 택한 이유는 자원 효율 — ①은 워커를 레인 수만큼 만들고 레인이 비면 그 워커가 논다. 대신 ②의 한계를 명시해야 한다: **이건 폴 단위 우선순위이지 선점이 아니다.** 이미 집어 든 batch가 끝나야 새로 온 run이 실행된다. 엄밀한 선점이 필요하면 레인별 동시성 슬롯을 나눈다. **교훈**: 우선순위 구현은 "어느 시점에 우선순위가 적용되는가"를 함께 문서화해야 오해가 없다. — 2026-07-26 20:30

### 토픽 자동 생성을 끄는 이유
`auto.create.topics.enable=true`(기본)면 존재하지 않는 토픽에 첫 메시지가 오는 순간 **파티션·보존 설정이 기본값으로** 토픽이 생긴다 — 의도한 파티셔닝·보존 정책과 무관하게 굳어버림. 명시 생성(init 스크립트/IaC)이 운영 규율. QoS 레인처럼 토픽이 계약의 일부면 더더욱. — 2026-07-26 19:38

### 같은 "소비"라도 작업 분배와 응답 수집은 반대 설정이 맞다
Kafka 소비엔 의미가 두 가지 있고 설정이 갈린다. **작업 분배**(요청 처리 — 한 메시지는 한 인스턴스만): 컨슈머 그룹 + 수동 커밋(at-least-once). **응답 수집**(request-response over Kafka — 내가 발행한 요청의 결과를 내가 받아야 함): **그룹을 쓰면 안 된다** — 워커 인스턴스가 여럿이면 내 요청의 응답이 다른 인스턴스로 로드밸런싱돼 영영 도착하지 않는다. 그룹 없이 전 파티션을 latest로 구독하고(모든 인스턴스가 모든 응답을 보고 자기 것만 집는다), 오프셋 커밋도 필요 없다(놓치면 타임아웃이 처리). problem 워커가 정확히 이 두 소비를 다 갖는다: `problem.generate`=작업 분배(그룹+수동 커밋), `submission.result`=응답 수집(그룹 없음). api의 SSE 팬아웃을 Redis pub/sub으로 한 것과 같은 구분 — **"누가 받아야 하는가"가 브로커 설정을 결정한다.** — 2026-08-03 21:10 ([ADR-0023](decisions/0023-problem-kafka-wiring.md))

## 백엔드 (api / Kotlin)

### 래퍼는 감춘 것을 없애주지 않는다 — reactor-kafka에서 배운 것

### Kotlin의 Int/Long은 wrapper가 아니다 — null 체크는 `?` 타입에만, 컴파일러가 강제하는 만큼만
Java 경험자의 자연스러운 걱정: "Kotlin 코드가 전부 `Long`·`Int`(wrapper처럼 보임)인데 null 체크가 남발되지 않나? primitive로 해야 하지 않나?" — **Kotlin에는 primitive/wrapper 이분법 자체가 없다.** 언어엔 `Long` 하나뿐이고 컴파일러가 non-null `Long`을 JVM primitive `long`으로 내려준다(박싱은 `Long?`·제네릭 등 Java에서도 wrapper가 강제되는 자리에서만). 핵심 차이는 **null 가능성이 타입에 인코딩**된다는 것: `Long`엔 null이 컴파일 타임에 못 들어가고, `Long?`에만 가능하며 체크는 그 타입을 쓰는 지점에서만 컴파일러가 강제한다. Java는 반대라서(모든 참조가 잠재적 null, 컴파일러 무개입) "혹시 몰라" 체크가 남발되거나 NPE가 난다. 스마트 캐스트(`if (x != null)` 후 자동 타입 좁힘)·`?.`·`?:`까지 더하면 체크 총량은 Java보다 적다. 우리 코드 실례: `Submission.userId: Long`=primitive+null 불가 보장 / `execTimeMs: Int?`=의도된 nullable("채점 전엔 값이 없다"는 도메인 사실의 타입 표현).

**우리 스택의 다른 언어들은 어떻게 푸나** — 언어는 두 축(① primitive 성능 ② null 안전)을 따로 푼다:
| 언어 | primitive | null 안전 |
|---|---|---|
| Java(실무) | 개발자가 primitive/wrapper 수동 선택 | 전 참조가 잠재적 null, 컴파일러 무개입 → 체크 남발/NPE |
| Kotlin(api) | 컴파일러 자동(non-null=primitive) | 타입 인코딩(`?`) + 강제 |
| Go(judge) | 전부 진짜 primitive(값 타입, 박싱 없음) | **nullable primitive가 아예 없음** — '없음'은 zero value·포인터(`*int64`)·`ok` 관용구로. 컴파일러 null 검사 없음(nil 패닉 가능)이나 zero value 문화로 nil 사용 자체를 줄임 |
| TypeScript(web) | `number` 하나(엔진이 최적화) | Kotlin과 같은 계열 — 유니온 타입(`number \| null`)+strictNullChecks 강제, narrowing=스마트 캐스트, `?.`·`??` 동일 |
| Python(problem·plagiarism 예정) | primitive 없음 — int도 전부 객체 | 런타임 방임. 타입 힌트(`int \| None`)+mypy를 얹어야 정적 규율(선택적) |

**경계에서 실제로 드러난 사례**: proto3 스칼라엔 null이 없어(기본값 0) judge(Go)는 "0=미측정" 규약으로 보내고, api(Kotlin)가 경계에서 `takeIf { it > 0 }`로 null로 번역한다 — 언어별 '없음' 표현의 차이는 서비스 계약에서 명시적 규약이 된다. — 2026-07-31 20:17 (사용자 질문 촉발, 타 언어 보강)

### "확실하지 않은 값을 도메인에 들이지 않는다" — Java primitive 관행의 일반화 (make illegal states unrepresentable)
사용자 실무 관행 — *"primitive를 쓰는 건 null 체크가 싫어서가 아니라, 확실하지 않은 값 위에서 비즈니스 로직이 돌지 못하게 막으려는 것"* — 은 일반 원리의 Java식 표현이다. 원리의 이름: **불법 상태는 표현조차 못 하게 하라** + **"검증하지 말고 파싱하라(parse, don't validate)"** — 경계에서 검증하며 *타입을 바꿔서*, 통과 이후의 코드는 컴파일러가 확실성을 알게 한다. Java는 이 도구가 primitive(숫자 한정)뿐이지만 다른 언어들은 더 일반적인 도구를 준다:
- **Kotlin**: non-null 타입이 primitive 관행의 **전 타입 확장** — `String`·`User`·`List`에도 "절대 null 아님"을 컴파일러가 보장. + `init`/`require`로 생성 시점 불변식(valid-by-construction).
- **Go**: zero value 철학(선언 즉시 확정값) + 생성자 함수가 검증 실패 시 값 자체를 안 내어줌(`(v, err)`) — 단 "0이 유효값인가 미설정인가"의 모호함이 남아 Kotlin보다 보장이 약하다.
- **TypeScript**: 유니온 타입+narrowing, 경계 파서(zod 등)가 unknown → 확실한 타입으로 변환.
- **Rust/FP(참고)**: `Option<T>` — '없음'이 명시적 컨테이너라 꺼내지 않으면 접근 자체가 컴파일 에러. 이 사상의 가장 순수한 형태(Java `Optional`은 그 모방이나 Optional 자체가 null일 수 있어 반쪽).
- **Python**: 언어 보장 없음 — pydantic(런타임 경계 검증)+mypy로 벌충. M3(Python 서비스) 때 도입 논점.

**우리 코드에 이미 있는 자리**: ① `CreateSubmissionRequest`(전부 nullable — 외부 입력의 불확실성) → `toCommand()` 검증 → `NewSubmission`(전부 non-null) — 불확실/확실 타입을 분리하고 경계에서 한 번만 변환 ② `NewSubmission.by: AuthPrincipal`(non-null) — "제출=로그인 필수" 규칙이 타입으로: 미인증 제출 커맨드는 생성 불가 ③ `TraceContext.parse()` — 통과하면 유효성이 타입에 보장 ④ judge `language.Lookup()` — 미지원 언어는 Spec을 안 줌 → executor는 확실한 Spec만 다룸. — 2026-07-31 20:17 (사용자 발제 논의)

### OAuth2는 "로그인 방식"이 아니라 프로토콜이다 — 프로바이더 없는 OAuth 로그인은 성립하지 않는다
"소셜 로그인(GitHub/Google) 말고 OAuth2 같은 것"이라는 표현은 범주 혼동이다 — **GitHub 로그인이 곧 OAuth2다**. OAuth2는 4역할(Resource Owner=사용자 / Client=우리 서비스 / Authorization Server=신원·권한 확인 주체 / Resource Server) 사이의 **권한 위임 프로토콜**이고, "OAuth로 로그인한다"는 말은 "Authorization Server 역할을 하는 **누군가(=프로바이더)**에게 신원 확인을 위임한다"는 뜻이다. 그 누군가가 GitHub·Google·카카오다. 위임받을 대상 없이 OAuth2만 쓰는 로그인은 정의상 불가능하다. 덧: 순수 OAuth2는 인가(authorization) 프로토콜이고, 이를 "로그인(인증)"에 쓰도록 표준화한 상위 레이어가 **OIDC(OpenID Connect)** — "구글로 로그인"의 정식 명칭은 OIDC다. 프로바이더 위임이 싫다면 남는 선택지는 ① 자체 가입(이메일+비밀번호 해시 — OAuth2 무관) ② **자체 Authorization Server 운영**(Keycloak 셀프호스팅, Spring Authorization Server 등 — 우리가 프로바이더가 되는 것). ②가 적합한 조건은 "여러 클라이언트 앱이 한 계정 체계로 SSO" 또는 "서드파티에 API 개방"이며, 퍼스트파티 클라이언트 1개(web)뿐인 서비스에선 자기 자신에게 위임하는 우회로만 남아 과설계다. 또한 **서비스 자체 세션 토큰 체계(JWT access/refresh)는 이 선택과 직교한다** — 신원 확인을 누가 하든, 확인 후 우리 서비스가 자기 토큰을 발급하는 구조는 동일하다. — 2026-07-30 21:42

### uv — 파편화된 파이썬 도구 체인의 통합 (사용자 문답)

파이썬의 고질은 도구 파편화다: 패키지 설치(pip)·가상환경(venv)·의존성 잠금(pip-tools/requirements.txt)·인터프리터 버전 관리(pyenv)·프로젝트 메타(setuptools/poetry)가 전부 별개 도구였다. **uv는 이걸 한 바이너리로 통합한 Rust제 도구**(ruff 만든 Astral 제작): `uv init`(스캐폴드)·`uv add`(의존성+잠금)·`uv sync`(환경 재현)·`uv run`(자동 동기화 후 실행)·`uv python`(인터프리터 설치까지). Node 세계로 치면 **pnpm+nvm을 합친 격**. 속도도 Rust+전역 캐시로 pip 대비 수십 배. 우리 채택 이유: ① `uv.lock`이 버전 진실원(web의 `packageManager` 원칙과 동일 — CI는 `uv sync --locked`로 로컬과 동일 환경 강제) ② 각 서비스가 자기 도구를 소유하는 모노레포 원칙에 부합(web=pnpm·api=Gradle wrapper·judge=go mod·**problem=uv**) ③ 신규 머신 온보딩이 `brew install uv` 한 번.

후속 문답(pip로 하면 안 되나 / 어디에 설치되나): pip로도 **되지만** pip는 "설치"만 담당한다 — 가상환경(venv)·전이 의존성 잠금(pip-tools)·활성화 관리를 손으로 조합해야 하고, 그 조합의 규율이 무너지면 "내 머신에선 되는데" 문제가 나온다(uv는 `uv add` 시점에 전이 그래프+해시를 lock에 자동 기록). **설치 위치는 3층으로 구분**: ① uv 자체=개발 머신(brew) ② 패키지=프로젝트 로컬 `.venv`(시스템 파이썬 오염 없음, gitignore) ③ 배포 시(M5)=컨테이너 이미지 빌드 안에서 `uv sync` — "서버에 설치"는 배포 마일스톤에서만 등장하는 개념이고 지금은 전부 개발 머신 로컬이다. — 2026-08-01 15:15 (15:17 보강)

### protoc의 Python 생성물은 proto 경로를 import 경로로 강제한다 — 생성 루트 = import 루트
Go는 `go_package` 옵션으로, Java는 `java_package`로 생성물의 패키지를 계약과 독립적으로 정할 수 있지만, **Python 생성기엔 그런 옵션이 없다** — `judge/v1/submission.proto`는 무조건 `judge/v1/submission_pb2.py`가 되고, 생성물끼리도 `from common.v1 import trace_pb2`처럼 **proto 경로 그대로의 절대 import**를 쓴다. 따라서 생성 출력 디렉토리가 곧 파이썬 import 루트여야 한다. 우리 해법: 생성 루트를 `services/problem/src`로 — `src/common`·`src/judge`는 새 최상위 패키지가 되고, `problem/v1`은 기존 `problem` 패키지의 서브패키지로 자연 편입된다(proto 패키지명과 서비스 패키지명이 같아서 오히려 맞아떨어진 경우). uv의 editable 설치가 `src/`를 통째로 sys.path에 올려 별도 장치 없이 동작. 흔한 대안(후처리로 상대 import 재작성 — protoletariat)은 도구가 하나 늘어 배제. **proto 패키지명이 서비스 패키지명과 충돌하는 구조였다면 이 배치는 불가능했다** — 폴리글랏에서 proto 패키지 이름은 각 언어의 모듈 체계까지 내다보고 지어야 한다. — 2026-08-03 21:10 ([ADR-0023](decisions/0023-problem-kafka-wiring.md))
